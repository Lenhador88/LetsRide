# Design — require a home country at onboarding

Mechanism, rejected alternatives, and the open questions. `proposal.md` is what changes;
`tasks.md` is the order. Everything below was measured against DEV `fpmrimzxadewsaiwpsel` and PROD
`zwprydcyryvudhurbnye` on 2026-09-07 unless it says otherwise.

---

## D1. Its own screen, not a second field on the username screen

**Decision: `/onboarding/country`, a third step, terminal.**

The alternative — a country control beside the username input, one submit — is cheaper and was
rejected on three counts:

1. **`setUsername`'s ordering contract does not survive it.** Its header states the rule: *"username
   first, RPC second, because a refused username must never leave a rider stamped complete with no
   username."* Folding the country in gives one submit two independent refusals (`23505` on the
   name, `23514` on the country) landing on one `ActionState` with one `error` string, and the
   `taken` field PD-146 added exists precisely because a refusal has to land on the *field*.
2. **The control is a searchable list of 249 rows, not a field.** It wants the screen. See §D7.
3. **The resume state is better, not worse, for being real.** A rider who picks a name and closes
   the tab currently comes back to a screen where their only work is already done and they must
   retype it. With two steps the name is already stored and they resume at the country.

The cost is one more screen in a wizard decision #5 says cannot be skipped, and it is the cost the
story asked for.

## D2. The country is NOT a stamp the guard reads, and `my_onboarding_state()` does not change

**This is the load-bearing decision in the change.** The obvious shape — add `has_home_country` to
the accessor, add a fourth field to `OnboardingState`, add a branch keyed on it — is unnecessary,
and it is expensive in exactly the place this repo has been burned.

The resume step is already fully determined by what the accessor returns today:

| `terms_accepted_at` | `has_username` | `onboarding_completed_at` | resume |
|---|---|---|---|
| NULL | — | — | `/onboarding/terms` |
| set | false | NULL | `/onboarding/username` |
| set | true | NULL | **`/onboarding/country`** |
| set | true | set | the app |

There is no reachable state where a rider has a country and no completion stamp, because the only
client path that writes the country during the wizard is `complete_onboarding` itself, which writes
both in one statement. So "has a country" adds no information the table above does not already
carry.

What that buys, and it is the reason to insist on it:

- **`my_onboarding_state()` keeps its return shape**, so the accessor is not a second thing with a
  deploy-ordering problem. A newer bundle destructuring a field an older function does not return
  reads `undefined`, which is falsy, which resolves to *"resume at country"* for **every rider on
  the app** — including onboarded ones, if the branch is misordered. That failure is a total
  lockout and it is invisible to `tsc`.
- **No fourth `GuardState`, no new `GuardSnapshot` field**, so `guard-cache.ts`'s generation
  counter, its `superseded`/`retry` outcomes and its five-writer safety property are untouched.
- **The country is never cached as a routing input**, so it cannot go stale in the one cache that
  is deliberately immutable for a session's lifetime.

**The new action is still a stamp writer.** It calls `complete_onboarding`, which writes
`onboarding_completed_at` — a field the decision does read — so it owes
`invalidateOnboardingState()` and `src/lib/actions/__tests__/writers-invalidate.test.ts` enforces
it. `setUsername` keeps its own invalidation: it still writes `has_username`, which the table above
now branches on, and it is no longer the terminal writer. **Both are needed and neither covers the
other.**

**The invalidation is necessary and was never sufficient**, and this change adds nothing to that
problem: PD-304's generation counter already discards a read that started before a write it
races. The country step's write is a rider-initiated submit, not a signup-time race, so it is the
benign end of that hazard.

## D3. The CHECK list is a third hand-kept copy of the country list, generated by script

`020` put the 249 assigned codes into a CHECK on `profile_countries.country_code`, generated from
`src/lib/countries.ts` rather than transcribed, and wrote down the standing risk: *"nothing
automatically reconciles the SQL copy with the TypeScript one."* This change makes it a third copy.

**Considered and rejected: a `private.is_assigned_country_code(text)` immutable function** shared by
both constraints. It reads better and is a worse trap — Postgres does not re-validate a CHECK when
the function behind it changes, so a list edited in the function silently leaves already-stored rows
violating a constraint that reports itself as valid. `014` and `020` both declined a `countries`
reference table, for the reason that stands unchanged: nothing joins against one, and it would be
249 rows of data this app never reads.

**So: generate the literal the way `020` did, and regenerate rather than edit by eye.** Both
constraints are kept for `020`'s own reason — the shape check names *case and shape* as the rule,
which is what `nl` and `NLD` violate, and the membership check names *assignment*, which is what
`ZZ` violates. Two constraints, two error identities.

## D4. Ordinary profile-column grants, not `025`'s server-owned posture

`025` revoked `authenticated`'s SELECT, INSERT and UPDATE on `terms_accepted_at` and
`onboarding_completed_at` outright, and `030` and `096` repeated it for `terms_version` and
`analytics_opt_out_at`. Four columns on this table are server-owned. Why the home country is not
the fifth:

**Every one of those four is evidence about a rider, produced by the server, that the rider must
not be able to author.** A consent timestamp the client can choose is not consent; a completion
stamp the client can write defeats decision #5. The home country is the opposite: it is a **fact
the rider states about themselves and is shown back to them**, like the town, the bike and the bio.
Its integrity question is *"is this a real country"*, which a CHECK answers completely, not *"who
said so and when"*, which only a grant can answer.

The practical consequence is the one that decides it: **a server-owned column cannot be edited**,
because the only reach would be a new `security definer` RPC per edit. `025`'s three RPCs exist
because those stamps genuinely have exactly three legitimate transitions. A country a rider picked
wrongly out of 249 has one obvious transition and no reason to route it through SQL.

**What keeps the grant honest is the trigger, not the grant.** §D5.

## D5. Once set, never removed — a coercion, and the editor field stays optional

`038` refuses a username removal by **coercion** — `new.username := coalesce(new.username,
old.username)` — rather than by a raise, one line above `enforce_onboarding_completion`'s
`old.onboarding_completed_at` early return, with a comment saying that position is not negotiable
because below it the rule is dead code for the entire population it protects. **The home-country arm
is that line again, with that placement, for that reason.**

Two properties fall out and both matter:

- **A coercion cannot take down a write.** The migration hangs new code inside every profile edit's
  own transaction, which is the hazard `112` owes a hand-exercise gate for. A raise there is a
  live outage on an already-shipped path; a `coalesce` is not. The gate is still owed (`tasks.md`
  §1.9) and it is cheap.
- **NULL → NULL is not a removal.** The arm is keyed on `old.home_country is not null`, so it never
  fires for the existing population, which is the whole population on day one.

**The profile editor's field is OPTIONAL, and that is not a hole.** Making it required would refuse
every existing rider's whole profile form until they answer — a re-prompt of the population the
Queued comment says to leave alone, arriving through the back door on a screen that is not the
wizard. It is `075` §4's defect with the sign flipped: that change had to make a field optional
because the wizard stopped collecting it; this one must keep a field optional because the wizard
started. A rider who has a country and blanks the control gets it coerced back and sees no error,
which is `038`'s accepted behaviour, asserted against the **stored value** rather than a SQLSTATE.

## D6. A country is a filter, never a position — and PD-419's chain is untouched

`resolveRiderLocation()` has two sources, `'device'` then `'profile'`, and `nearLabel` exists
because *"the name must come from the same source as the number"*. A country has no centroid worth
having: the centroid of the Netherlands is a field near Lunteren, and every distance measured from
it would be wrong by up to 150 km while looking exactly like a real number.

**So the country adds no `RiderLocationSource`, no centroid lookup, and no `near` label.** A rider
with a country and no town and no device fix still has *no position*, and `nearLabel` still returns
`null` for them — which is the correct claim, because the app does not know where they are. What
the country buys is a **filter** — `Explore rides in the Netherlands` — and PD-427 owns those words.

This is also the line that keeps the story from becoming a reason to force the OS prompt. The
requirement is legitimate *because* a form field answered is consent and an OS prompt with no
escape is not. Nothing in this change may narrow PD-419's decline rule, and there is no IP lookup
at any point.

## D7. There is no Select primitive, and the drawn container does not transfer

**Two findings from the committed snapshot, both of which cost a build session if they are found
late.**

**`src/components/ui/` has no Select, no Dropdown and no single-select list.** It holds `Input`,
`Textarea`, `Checkbox`, `ButtonGroup`, `PlaceSearchField`, `ContextMenu` and eighteen others; the
nearest thing is `PlaceSearchField` (a search-and-pick over remote results) and
`ProfileCountries.tsx` (a **multi**-select over `COUNTRY_CODES` with checkboxes, backing the travel
log). **A single-select country picker is a new shared primitive**, not a screen-local component,
and it belongs to `design-system` rather than to whoever builds the screen — a second bespoke
picker is how two of them end up in the tree.

**The drawn screen is `Login / Onboarding › Add your location`, and most of it must not be used.**
`npm run figma -- tree "Add your location"` (offline, per `CLAUDE.md`; the API is never called):

- Footer: a **3-dot `Pagination`**, a **`Skip`** secondary button and a `Next` primary. `Skip`
  contradicts decision #5 outright and contradicts this story's own requirement; the 3-dot count
  is the pre-`075` wizard's, and the wizard after this change has **three** screens again — which
  is a coincidence, not a reason to keep the component. The username screen removed `Pagination`
  entirely when it became the only step, and whether it comes back is Q3.
- Form: a **`City` text input** under the title *"Where are you located?"*. There is **no country
  control drawn anywhere in the onboarding flow.** `Component / Search Results / Country` exists —
  a 24×18 flag, a `Poppins/16/Regular` label and a **checkbox** — and the checkbox is the travel
  log's multi-select, so the row transfers and its selection affordance does not.
- A `Back` link, which is legitimate here: unlike the username screen (`Q12`: "back to signup is
  meaningless once the account exists") this step genuinely has a previous one.

`docs/specs/login-onboarding.md` records the onboarding frames by node id and is **history, not a
template** — `CLAUDE.md` §The Agent Squad. Read it for the node ids only.

## D8. Two migrations, and why the arming file cannot be folded in

`proposal.md` §Sequencing carries the table. The part worth keeping here is the general shape,
because it is the third time this repo has hit it: **`108`/`109` split for the same reason, and the
rule that produces the split is that the additive half and the restrictive half want opposite sides
of the same deploy.** `113` must exist before the new bundle can write a column; `114` must not
exist until the old bundle has stopped calling a function that would now be refused. One file
cannot be both.

`114` is small enough to look like tidiness that could ride along with `113`. It is the entire
requirement.

## Open questions

Each carries a recommended default so nothing stalls. **None is blocking** — every one has an
answer the build can proceed on and correct later.

### Q1 — Is anything preselected in the picker? *(non-blocking · product owner)*

**Recommended default: nothing is preselected, and the submit stays disabled until the rider
chooses.**

A rider who taps through a preselected `NL` has told us nothing, and the value is indistinguishable
from one they meant. Deriving it from `navigator.language` or the device time zone is the same
trade PD-419 refused for IP and refused for a reason — a guessed location that looks stated is
worse than an absent one, and this column's whole value is that it cannot be subtly wrong.

Ordering the list is a separate and smaller question; alphabetical by `Intl.DisplayNames` name in
the rider's own locale is what `ProfileCountries` already does.

### Q2 — Does the country step also collect the optional town? *(non-blocking · agent's call unless overridden)*

**Recommended default: no. The country screen collects exactly one thing.**

The town is already reachable in the profile editor, and PD-419 owns the *"where are you at"* ask
on Explore. Putting an optional field on a required step re-creates the `Skip` ambiguity the design
draws and decision #5 forbids — a rider cannot tell which half of the screen is the gate.

### Q3 — Does `Pagination` come back? *(non-blocking · design-system)*

**Recommended default: yes, `total={3}` across terms, username and country.**

The username page removed it with the comment *"a one-dot progress bar communicates nothing"*,
which stops being true at three. The counter-argument is that `/onboarding/terms` is not a wizard
step for most riders — it is a prompt for accounts whose consent predates the signup write — so a
3-dot bar over what is usually a 2-screen flow overstates it. `total={2}` over username and country
is the defensible alternative; either is better than the current absence, and neither is worth
holding the build for.

### Q4 — What does the screen say? *(non-blocking · product owner)*

**Recommended default: reuse the drawn title verbatim — *"Where are you located?"* — with the
control labelled `Country` and one line of subcopy saying the town is optional and comes later.**

The drawn copy is the only copy that exists and it is honest for a country. What it must **not**
say is anything promising proximity (§D6), and it must not offer a skip (decision #5).
