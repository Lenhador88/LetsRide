# ride-chat-unread

> **New capability.** `ride-chat` owns who is in a conversation; this owns **what a rider has
> already seen of it**, and the one mark the design draws to say so.
>
> Every requirement below is a statement about a role and a resource, so each maps onto an
> assertion in `supabase/tests/rls_test.sql`. Two exceptions are named as such where they appear:
> whether the mark advances on a message arriving over Realtime is a client behaviour with no
> Postgres assertion behind it, and the *rendering* rules for the dot are `client-render-shell`'s
> shape rather than a policy.

## ADDED Requirements

### Requirement: The unread mark SHALL be a per-rider, per-ride watermark and SHALL NOT be a per-message read table

Unread state SHALL be stored as one row per `(rider, ride)` carrying a single timestamp. It SHALL
NOT be stored as a row per message seen, and it SHALL NOT be computed by fetching a thread and
counting in the client.

This is `015`'s model transferred, and the argument transfers with it unchanged: a watermark's row
count is bounded by **membership**, so a rider on five rides holds five rows for ever, while a
per-message table grows as riders × messages — and a chat is the one table in this schema with no
natural ceiling. `ride-chat` already states the ceiling problem for reads; a read-receipt table
would put the same unbounded growth on the *write* path, generated by scrolling.

The cost is the same cost `015` states rather than a new one: a watermark can only express
"everything older than T is read", never a prefix of a thread. That is honest here for a reason
the feed had to argue for — a chat is read oldest-first to the end, so the rider who has the
screen open **has** read to the end.

#### Scenario: One row per rider per ride, and no more
- **WHEN** a rider reads a ride's chat any number of times
- **THEN** at most one watermark row SHALL exist for that `(rider, ride)` pair
- **AND** the row count SHALL be bounded by crew membership rather than by message volume

#### Scenario: No per-message read state is introduced
- **WHEN** unread state is stored
- **THEN** no table SHALL record that a specific rider saw a specific message
- **AND** no column SHALL be added to `ride_messages` to carry read state, because that would be
  the same growth in a different shape

#### Scenario: The key needs no `nulls not distinct`, and that SHALL be stated rather than copied
- **WHEN** the uniqueness of `(user_id, ride_id)` is expressed
- **THEN** it SHALL be a **primary key**, because both columns are NOT NULL — there is no
  "app-wide ride" the way `feed_reads.club_id IS NULL` is the app-wide feed
- **AND** `unique nulls not distinct` SHALL NOT be copied from `015`, because it is meaningless
  where no NULL can occur and copying it would state a rule the table does not have
- **AND** the primary key SHALL be what the upsert's `on conflict` names, since a primary key is
  already a unique constraint

### Requirement: A rider SHALL write a watermark only for themselves, and only for a chat they can actually read

The INSERT and UPDATE policies SHALL require `user_id = auth.uid()` **and** that the caller is on
the chat's audience — the same **intersection** `034`'s SELECT policy uses: an `EXISTS` against
`rides` evaluated under the caller's own row security **AND** `private.is_ride_crew(ride_id)`.

**The reason for the second conjunct is `015` §2's, not `034`'s, and the difference is worth
stating because the obvious reading is wrong.** A watermark row grants nothing: it cannot make a
message readable, and `ride_has_unread` never consults it for authorization. So `034`'s leak
argument — that the crew helper alone lets an ex-club-member *read* a chat — does not transfer to
a `WITH CHECK`, which grants no reads at all. What does transfer is `015`'s: without an audience
predicate the foreign key turns an INSERT into an existence oracle, because a nonexistent ride id
raises `23503` while an existing-but-invisible one succeeds.

**The full intersection is nonetheless required, rather than the crew helper alone, for three
reasons stated so the choice is not re-litigated as over-engineering:**

1. It makes the watermark's audience **exactly** the chat's audience, so no row can ever assert
   that a rider read a thread they cannot open.
2. `private.is_ride_crew` is `security definer` and its own comment says it is "half of a
   conjunction by design; on its own it is a leak". Using it as a sole conjunct anywhere
   establishes that it is usable alone, and the next table copies it into a SELECT policy. That is
   `034`'s `is_club_member` trap in a new costume.
3. The refusal costs nothing real: a rider who satisfies the crew conjunct but fails the
   visibility one already reaches a 404 on the ride, so no screen issues the write.

#### Scenario: A rider cannot write a watermark for another rider
- **WHEN** a rider inserts or updates a `ride_reads` row naming a `user_id` that is not their own
- **THEN** the write SHALL be refused
- **AND** this SHALL hold on the UPDATE arm's `USING` as well as its `WITH CHECK`, so a rider
  cannot move an existing row out of their own ownership

#### Scenario: A rider who can see the ride but is not on its crew is refused
- **WHEN** a signed-in rider who is not the organizer and holds no `ride_members` row writes a
  watermark for a ride they *can* see
- **THEN** the write SHALL be refused
- **AND** the refusal SHALL be attributable to the crew conjunct, asserted in isolation

#### Scenario: A rider who cannot see the ride is refused identically to one naming a ride that does not exist
- **WHEN** a rider writes a watermark naming a private club's ride they are not in, and separately
  naming a UUID no ride carries
- **THEN** both SHALL be refused
- **AND** both SHALL be refused by row security **before** the foreign key is evaluated, so the two
  are indistinguishable and the write is not an existence oracle

#### Scenario: A crew member who blocked the organizer is refused
- **WHEN** a crew member blocks the ride's organizer, in either direction, and their `ride_members`
  row is untouched
- **THEN** the watermark write SHALL be refused
- **AND** the refusal SHALL come from the ride-visibility conjunct, asserted in isolation, because
  the crew conjunct alone would admit them

#### Scenario: A crew member who left the ride's private club is refused
- **WHEN** a rider holding a `ride_members` row for a private club's ride leaves that club
- **THEN** the watermark write SHALL be refused
- **AND** this SHALL be asserted separately from the blocking case, because a single assertion
  cannot say which conjunct did the work

#### Scenario: A rider who left the crew is refused, and their row survives
- **WHEN** a rider sets their attendance to `No`, deleting their `ride_members` row
- **THEN** further watermark writes SHALL be refused
- **AND** the row they already hold SHALL remain, because nothing cascades on leaving — the
  foreign key is to `rides`, not to `ride_members`
- **AND** rejoining SHALL reuse that row, so messages sent while they were away read as unread,
  which is correct

#### Scenario: The organizer with no `ride_members` row can write
- **WHEN** the rider named in `rides.organizer_id` writes a watermark while holding no
  `ride_members` row at all
- **THEN** the write SHALL succeed, through `private.is_ride_crew`'s organizer arm
- **AND** this SHALL NOT depend on `enforce-creator-membership` shipping first

#### Scenario: A signed-out visitor reaches nothing
- **WHEN** a request against the watermark table arrives with no session
- **THEN** every read SHALL return zero rows and every write SHALL be refused, because `anon` holds
  no grant on the table
- **AND** this change SHALL add none, per decision #1

### Requirement: A watermark SHALL NOT be readable by anyone but its owner, and this app SHALL NOT have read receipts

The SELECT policy SHALL be `user_id = auth.uid()` and nothing wider. No rider, including the ride's
organizer, SHALL be able to learn whether another rider has read the chat, or when.

**A watermark is behavioural personal data about an identified person — when they last looked at a
conversation.** It is the most disclosive row this change adds, and it is more disclosive than
anything `015` stores, because a ride's chat has a named, small audience: "the organizer can see I
read at 03:40" is a fact about a specific rider on a specific night. `ride_messages` deliberately
draws no delivery or read state and the design draws none; the absence is the decision, not an
unbuilt feature.

#### Scenario: Nobody reads another rider's watermark
- **WHEN** any rider — a crew member, the organizer, a club owner or a club admin — selects from
  the watermark table
- **THEN** only their own rows SHALL be returned
- **AND** the assertion SHALL name the organizer specifically, because the organizer is the role a
  future "who has seen this" affordance would be built for

#### Scenario: No screen renders a read receipt
- **WHEN** the chat, the crew page or the ride plan is rendered
- **THEN** nothing SHALL indicate whether any other rider has read anything
- **AND** no tick, timestamp, avatar row or "seen by" count SHALL be added, because the data to
  draw one is deliberately unreachable

### Requirement: The unread answer SHALL be computed under the caller's own row security, and SHALL NOT be denormalised

The dot SHALL be answered by a `security invoker` function in `public` that reads `ride_messages`
under the caller's own RLS. It SHALL NOT be answered by a counter column, a trigger-maintained
total, or any `security definer` path.

This is `015` §4's ruling and `client-cache-invalidation`'s existing rule about definer-rights
counts, and here it does more work than it does for clubs: `034`'s SELECT policy carries the
crew conjunct, the ride-visibility conjunct **and** the symmetric block arm on the author, so an
invoker function inherits all three for free and can return nothing the caller could not already
read. A denormalised counter would need every one of them restated, per viewer, which is not
expressible in a column.

A trigger maintaining a per-crew-member counter is refused for `015`'s second reason as well: it
would fan out one write per crew member inside the sender's own transaction, on the hottest write
path in the app.

#### Scenario: The function is INVOKER and lives where PostgREST can publish it
- **WHEN** the reader function is created
- **THEN** it SHALL be `security invoker`, `stable`, and `set search_path = ''`
- **AND** it SHALL therefore add no `authenticated_security_definer_function_executable` advisor
  finding, and the advisor count SHALL be unchanged by this change

#### Scenario: Publishing it discloses nothing
- **WHEN** any signed-in rider calls the function with any ride id, including one they cannot see
  and one that does not exist
- **THEN** it SHALL answer `false` rather than raising
- **AND** the two SHALL be indistinguishable, so the RPC is not an existence oracle either

#### Scenario: `anon` cannot call it
- **WHEN** the grants are written
- **THEN** EXECUTE SHALL be revoked from `public` and `anon` and granted to `authenticated` only
- **AND** the assertion SHALL name the role rather than calling the function, because the suite
  runs as the table owner for whom no barrier exists

#### Scenario: A blocked rider's message SHALL NOT light anybody's dot
- **WHEN** a crew member the viewer has blocked, in either direction, posts a message
- **THEN** the viewer's dot SHALL NOT light
- **AND** no block filter SHALL appear in the function body, the data layer or the component,
  because `034`'s SELECT policy already excludes the message and the function reads through it

### Requirement: A rider's own messages SHALL NOT light their own dot

The unread answer SHALL exclude messages authored by the caller.

**A dot that lights on your own send is plainly wrong**, and it is reachable without any race: the
rider sends from the chat screen and taps back. Excluding own messages makes the answer correct
independently of whether the watermark advanced first, which is the property that matters — the
alternative depends on a second write winning a race with a navigation.

**This diverges from `015`, which does not exclude the reader's own postcards from
`club_unread_counts()`, and the divergence is deliberate rather than an oversight.** A postcard is
authored from `/postcards/new` rather than from inside a club, so that counter can badge a club for
the reader's own postcard. That is a candidate defect in `015`; it is recorded here and **not fixed
here**, because it is a different table's function and a separate change.

#### Scenario: Your own message does not badge you
- **WHEN** a rider posts a message and then reads the unread answer for that ride
- **THEN** it SHALL be `false`, whether or not their watermark has advanced past their own message

#### Scenario: Somebody else's message does badge you
- **WHEN** another crew member posts a message newer than the reader's watermark
- **THEN** the answer SHALL be `true`

### Requirement: A rider with no watermark SHALL have a defined starting point, including the organizer who holds no crew row

Where no watermark row exists, the comparison point SHALL be the rider's `ride_members.joined_at`;
where no `ride_members` row exists either, it SHALL be the ride's own `created_at`.

`015` uses `coalesce(watermark, joined_at)` so that joining a five-year-old club does not badge it
with everything ever posted, and the first arm transfers unchanged. **The second arm is new and is
required**, because `034` §1 establishes that the organizer may hold no `ride_members` row at all —
`createRide` writes it as a second round trip with no transaction, and `enforce-creator-membership`
is unshipped. A two-arm `coalesce` would return NULL for that rider and the comparison would answer
`false` for ever: **the host would be the one person in the crew whose dot never lights.**

`rides.created_at` is equivalent to "since the beginning" for this purpose, since no message can
predate its own ride, and it is a column that always exists.

#### Scenario: A crew member who has never opened the chat sees messages since they joined
- **WHEN** a rider with no watermark row reads the unread answer
- **THEN** messages posted after their `joined_at` SHALL light the dot
- **AND** messages posted before they joined SHALL NOT

#### Scenario: The organizer with no crew row is not silently excluded
- **WHEN** the organizer holds no `ride_members` row and no watermark row
- **THEN** any message from another rider SHALL light their dot
- **AND** the fallback SHALL be asserted directly against that state, because it is reachable today
  rather than only in theory

#### Scenario: The fallback stops mattering when the crew row exists
- **WHEN** `enforce-creator-membership` ships and the organizer holds a `ride_members` row
- **THEN** the third arm SHALL remain in place rather than being removed as dead, for the reason
  `ride-chat` already gives for the organizer arm of `is_ride_crew`: a privileged path can still
  remove the row, and a host whose dot never lights is a silent failure

### Requirement: The watermark timestamp SHALL be generated by the database, never by the device

`last_read_at` SHALL be imposed by a `BEFORE INSERT OR UPDATE` trigger that discards whatever the
client sent. A column DEFAULT SHALL NOT be treated as the enforcement.

**The decisive argument is not tamper-resistance, it is that the two sides of the comparison must
share a clock.** The unread answer compares `last_read_at` against `ride_messages.created_at`,
which `034` §4b makes server-generated precisely so a device clock never orders a conversation.
Letting the client supply the other operand puts a phone's clock on one side of a comparison and
the database's on the other: a device running ten minutes fast silently marks as read every message
that arrives in the next ten minutes, and a slow one re-lights the dot on messages the rider has
seen. Nothing anywhere goes red.

A DEFAULT cannot do this job — it applies only when the column is **omitted**, and PostgREST will
name it.

**Corrected at build time: withholding the column grant, `034` §4b's mechanism, is not blocked by
the reason first written here, and that reason must not be repeated.** It said the upsert's UPDATE
arm "must name `last_read_at`", so revoking the grant would fail `42501`. It would not — PostgREST
builds `on conflict … do update set` over the columns present in the request *body*, so a client
that omits the column needs no privilege on it. The real constraint is narrower: with the column
absent from the body, what ADVANCES the value on the UPDATE arm is the trigger, and what makes the
statement reach the trigger is PostgREST's SET-list construction — an external tool's behaviour
rather than a database guarantee, and one the RLS suite cannot observe because it speaks SQL and not
HTTP. So the writer SHALL send the column, the grant SHALL permit it, and the trigger SHALL make the
value true regardless: two visible mechanisms, neither inferred.

#### Scenario: A client-supplied timestamp is overwritten, not merely ignored
- **WHEN** a rider upserts a watermark naming `last_read_at` with any value, past or future
- **THEN** the stored value SHALL be server time
- **AND** this SHALL hold on the UPDATE arm as well as the INSERT arm, because the upsert reaches
  the table through both

#### Scenario: The trigger takes no caller input and is not callable
- **WHEN** the trigger function is created
- **THEN** it SHALL take no argument, SHALL derive the value from the server alone, and SHALL have
  EXECUTE revoked from `public`, `anon` and `authenticated`
- **AND** it SHALL therefore add no advisor finding

#### Scenario: The already-shipped instance is recorded rather than silently inherited
- **WHEN** this rule is written down
- **THEN** `feed_reads.last_seen_at` SHALL be recorded as carrying the same defect — `markClubSeen`
  and `markFeedSeen` both send `new Date().toISOString()` and it is compared against
  `postcards.created_at` and `rides.created_at`
- **AND** this change SHALL NOT fix it, because it is a different table on a shipped path, but the
  new table SHALL NOT copy the pattern on the grounds that the existing one does

### Requirement: The watermark SHALL advance while the rider is on the screen, not only when they arrive

The mark SHALL be written when the chat screen mounts for a crew member, **and again whenever a
message arrives while it is mounted**.

PD-119 shipped live delivery, so the common case is that the rider is looking at the thread when
the next message lands. A mark written only on mount means the dot lights the instant they navigate
back to the ride plan, showing them a message they watched arrive — which is the single most
visible way this feature can be wrong, and it is the normal path rather than an edge case.

#### Scenario: Arriving on the screen marks the thread read
- **WHEN** a crew member opens the chat
- **THEN** the watermark SHALL advance
- **AND** the write SHALL be keyed on the ride alone, so a re-render does not re-fire it

#### Scenario: A message arriving while the screen is open advances it again
- **WHEN** a message arrives over the live stream while the rider has the chat open
- **THEN** the watermark SHALL advance again once that message is on screen
- **AND** the trigger SHALL be the newest rendered message changing, not a timer and not the
  subscription callback alone, so a message the rider has not been shown cannot be marked read

#### Scenario: Leaving and returning does not re-light the dot
- **WHEN** a rider reads the chat to the end and navigates back to the ride plan
- **THEN** no dot SHALL be drawn
- **AND** this SHALL hold whether the last message arrived before they opened the screen or while
  they were on it

#### Scenario: Only a crew member marks a thread read
- **WHEN** a rider who is not on the crew reaches the chat screen
- **THEN** no watermark write SHALL be issued at all
- **AND** the rule SHALL be expressed by whether the marking component is mounted, not by a
  condition inside an effect that runs regardless — matching `MarkClubSeen`
- **AND** the database SHALL refuse the write regardless, so the conditional mount is an
  optimisation and not the enforcement

#### Scenario: A hidden tab defers the mark rather than taking it
- **WHEN** messages arrive while the chat is mounted but the document is not visible — a backgrounded
  tab, or a phone in a pocket
- **THEN** the watermark SHALL NOT advance, because nobody has seen them
- **AND** it SHALL advance when the document becomes visible again, so the effect is a deferral and
  not a loss
- **AND** visibility SHALL be the test rather than focus, because a thread behind a dialog or beside
  another window is still being read

#### Scenario: A failed mark is silent
- **WHEN** the watermark write fails
- **THEN** nothing SHALL be shown to the rider and the screen SHALL be unaffected
- **AND** the consequence — a dot that lights again on the next visit — SHALL be accepted as the
  correct failure direction, because it over-reports unread rather than hiding a message

### Requirement: The mark SHALL be a dot and SHALL NOT be a count

The unread answer SHALL be a boolean and the rendered mark SHALL be `NotificationDot` unchanged. No
number SHALL be produced, cached or rendered.

The design draws `v2 / Component / Notification` at 16×16 on the chat-bubble button — measured in
`Ride - Ride plan - Sub pages` (`2375:9114`) and `Ride - Crew (Riders)` (`2375:9212`), visible in
both, while the same component sits `[hidden]` on the back and Options buttons of every ride frame.
`NotificationDot`'s own docstring records that the Figma component carries a `Notifications` text
property with **no text layer rendering it**; `v2 / Component / Counter` is the component that draws
a number and it is not used here.

**A boolean is also the cheaper and more honest computation**, and this is where this change
improves on `015` rather than copying it. `015` had to cap each subquery at 100 because a count
scans; an `exists` short-circuits on the first qualifying row and needs no cap, so the answer is
genuinely O(1) in thread length through the `(ride_id, created_at, id)` index `034` already
created. A number that is computed but not drawn is a number somebody renders later.

#### Scenario: No count is produced
- **WHEN** the unread answer is computed
- **THEN** it SHALL be a boolean
- **AND** no capped-count subquery SHALL be written, because there is nothing to cap

#### Scenario: The existing primitive is reused unchanged
- **WHEN** the dot is drawn
- **THEN** it SHALL be `NotificationDot`
- **AND** no component under `src/components/ui/` or `src/components/icons/` SHALL be added or
  modified by this change

#### Scenario: The dot sits on the control it describes
- **WHEN** the ride plan or the crew page renders the chat-bubble button
- **THEN** the dot SHALL overlay that button
- **AND** it SHALL NOT be drawn on the chat screen itself, which draws no chat button

### Requirement: The dot SHALL define every state it can be in, and SHALL NOT render a stale or speculative mark

The mark SHALL be absent unless the answer is a fresh `true`.

`client-cache-invalidation` already rules that a failed count shows nothing rather than a stale
value, for the reason `NotificationsHeaderControl` records: a dot the rider cannot clear by
visiting the screen is worse than a missing one. The same rule is restated here for the states a
*ride* adds — a viewer who is not crew, and a ride that is still loading.

#### Scenario: Not answered yet draws nothing
- **WHEN** the unread read has not resolved, on the first render tick or during a refetch
- **THEN** no dot SHALL be drawn
- **AND** flashing a dot ahead of an answer that may be `false` SHALL be treated as the same defect
  as a stale one

#### Scenario: A failed read draws nothing and no error
- **WHEN** the unread read fails, including offline
- **THEN** no dot SHALL be drawn, no error state SHALL be rendered, and no retry SHALL be offered
- **AND** the ride plan and crew screens SHALL render exactly as they do today, because the mark is
  a decoration on a control that works without it

#### Scenario: A non-crew rider triggers no read at all
- **WHEN** a rider who is not on the crew opens the ride
- **THEN** no chat button SHALL be drawn, so no unread read SHALL be issued
- **AND** the permission-denied case SHALL therefore never reach the rider as an empty state,
  because the control that would carry it is absent

#### Scenario: An empty thread is not a dot
- **WHEN** a ride's chat has no messages at all
- **THEN** the answer SHALL be `false` and no dot SHALL be drawn
- **AND** this SHALL be indistinguishable from a thread the rider has read to the end, which is
  correct — both mean "nothing here for you"

#### Scenario: The dot is answered on mount and does not track arrivals
- **WHEN** a rider is looking at the ride plan or the crew page and another rider posts
- **THEN** the dot MAY remain absent until the screen is next mounted, and this SHALL be understood
  as the feature's refresh boundary rather than a defect
- **AND** the key's nesting under the thread's SHALL NOT be cited as delivering live freshness: the
  only writer of that key runs in the author's own browser about their own message, which never
  lights their own dot, so the reach is correct and inert
- **AND** the dot SHALL be correct whenever it is drawn, which is what the boundary buys — a badge on
  a control the rider must navigate to in order to see is answered at the moment they can see it

#### Scenario: A partial failure costs only the dot
- **WHEN** the unread read fails while the ride read succeeds
- **THEN** the ride plan SHALL render in full
- **AND** the failure SHALL NOT propagate to the screen's error state

### Requirement: Watermarks SHALL die with their ride and their rider, and their retention SHALL be stated

Both foreign keys SHALL be `ON DELETE CASCADE`. There SHALL be no DELETE policy and no DELETE grant,
and the absence of any expiry SHALL be recorded as a decision rather than left unstated.

**Leaving the crew SHALL NOT remove the row, and this SHALL be stated rather than assumed.** `015`'s
§2 comment says *"Leaving a club cascades the row away via the FK"*; that is not what the foreign
key does — `feed_reads.club_id` references `clubs(id)`, so the cascade fires when the **club** is
deleted, not when membership ends. Inheriting that sentence here would state a retention guarantee
the schema does not give.

#### Scenario: Deleting the ride destroys its watermarks
- **WHEN** a ride is deleted
- **THEN** every watermark row for it SHALL be removed by cascade

#### Scenario: Deleting an account destroys that rider's watermarks everywhere
- **WHEN** a rider deletes their account
- **THEN** every watermark row they hold SHALL be removed by cascade from `profiles`

#### Scenario: An organizer's deletion takes every crew member's watermarks for their rides
- **WHEN** a rider who organises rides deletes their account
- **THEN** those rides cascade away and every crew member's watermark rows for them go too
- **AND** this SHALL be stated as a consequence of the erasure rather than discovered, because it is
  two cascade levels deep and invisible in any single foreign key

#### Scenario: Leaving the crew leaves the row standing
- **WHEN** a rider leaves a ride's crew
- **THEN** their watermark row SHALL survive, inert, until the ride or the rider is deleted
- **AND** rejoining SHALL reuse it rather than starting from `joined_at` again

#### Scenario: Nobody can delete a watermark
- **WHEN** any rider attempts to DELETE from the watermark table
- **THEN** it SHALL be refused by the absent grant as well as the absent policy
- **AND** the assertion SHALL be scoped to the grantee —
  `has_table_privilege('authenticated', 'public.ride_reads', 'delete')` — never a table-wide grant
  count, which reads 2 against a correct database because `postgres` and `service_role` hold
  everything by Supabase default

#### Scenario: There is no expiry, and that is recorded
- **WHEN** this change ships
- **THEN** no scheduled deletion SHALL exist, so a watermark lives as long as its ride
- **AND** retention SHALL be understood as indefinite and owned by the product owner as an open
  question with a stated default, matching the ruling `ride-chat` already made for messages

### Requirement: Every role's reach into a ride's unread state SHALL be stated

Every role below SHALL have the reach the table gives it and no other, and each row SHALL have at
least one assertion behind it in `supabase/tests/rls_test.sql`.

| Role | Read own watermark | Write own watermark | Read another rider's watermark | Dot lights |
|---|---|---|---|---|
| Ride organizer (crew row or not) | Yes | Yes | **No** | On other riders' messages |
| Crew member, `going` or `maybe` | Yes | Yes | **No** | On other riders' messages |
| Crew member who blocked the organizer | Own rows only | **No** | **No** | **Never** — no chat |
| Crew member the organizer blocked | Own rows only | **No** | **No** | **Never** — no chat |
| Crew member who left the ride's private club | Own rows only | **No** | **No** | **Never** — no chat |
| Rider who left the crew | Own rows only | **No** | **No** | **Never** — no chat button |
| Signed-in rider who can see the ride, not crew | n/a — no row | **No** | **No** | **Never** — no chat button |
| Signed-in rider who cannot see the ride | n/a — no row | **No** | **No** | **Never** |
| Club owner / club admin of the ride's club, not crew | n/a — no row | **No** | **No** | **Never** — the club roles confer nothing here |
| Blocked author's message | n/a | n/a | n/a | **Never lights the blocker's dot** |
| Rider with `terms_accepted_at` NULL | n/a — no row | **No** | **No** | **Never** — cannot be crew |
| Signed-out visitor (`anon`) | **No** | **No** | **No** | **Never** |

`club_members.role` has had `admin` since `001`, and neither `admin` nor a club's `owner` appears
in `private.is_ride_crew`. A club role therefore confers **no** reach into a ride's chat or its
unread state, and that is stated here because it is the assumption most likely to be made silently.

#### Scenario: Each row of the table is an assertion
- **WHEN** the RLS suite is written
- **THEN** every row above SHALL have at least one assertion behind it
- **AND** the three "no chat" rows SHALL each be asserted against the conjunct that refuses them, so
  that removing either conjunct fails a different case

#### Scenario: An un-consented rider is refused, and the chain that refuses them is asserted
- **WHEN** a rider whose `terms_accepted_at` is NULL writes a watermark for a ride they can see
- **THEN** it SHALL be refused — not by a participation-gate trigger on this table, which it
  deliberately does not carry, but because `023`'s gate on `ride_members` stops them acquiring the
  crew standing the `WITH CHECK` requires
- **AND** **both links SHALL be asserted**, because the argument is transitive and the gate is
  narrower than "every write": an account created by calling GoTrue's `/auth/v1/signup` directly
  reaches real write paths with the stamp NULL, so an unasserted chain is exactly the assumption
  that "silently becomes whatever the migration author assumed"

#### Scenario: A club admin gains nothing
- **WHEN** a club's admin or owner, who is not on a ride's crew, reads or writes unread state for
  that ride
- **THEN** they SHALL reach nothing and write nothing
- **AND** the refusal SHALL come from `private.is_ride_crew`, which knows nothing about club roles

### Requirement: The surfaces this change does not build SHALL be named rather than half-built

A Rides-tab badge, a badge on the rides list cards, a badge on the sub-page switcher's Chat row,
read receipts, per-message read state and mute SHALL NOT be rendered as inert or partial controls.

Each has a reason and the reasons are different, which is why they are listed rather than covered by
one sentence:

- **The Rides tab and the rides list cards** — the design draws neither. `Home - Rides - All`
  (`1891:2020`) carries a `v2 / Component / Notification` on its header button and two
  `v2 / Component / Counter` instances on ride rows, and **all three are `[hidden]`**; the
  navigation bar's `Rides` tile carries no notification instance at all, even with `--all`. Building
  a rollup would be inventing a surface, and it would need a plural reader this change deliberately
  does not create.
- **The sub-page switcher's Chat row** — the design puts the dot on the icon and nowhere else. This
  sits in tension with the PD-101 measurement that riders could not find the icon at all, which is
  recorded as an open question rather than resolved by guessing.
- **Read receipts** — refused by the watermark's own SELECT policy above, as a decision.
- **Mute** — suppresses notifications that do not exist for chat, exactly as `ride-chat` already
  records for the Options sheet.

#### Scenario: No tab or list badge ships
- **WHEN** the Rides tab, the rides list or a ride card is rendered
- **THEN** no unread mark SHALL be drawn
- **AND** no plural unread function SHALL be created "for later", because an RPC with no caller is
  the same artifact as a control that renders and does nothing

#### Scenario: Widening later is a change, not a fill-in
- **WHEN** a rollup is eventually wanted
- **THEN** it SHALL be specified as its own change, including how a badge summarising many rides is
  cleared, which this change deliberately does not answer
- **AND** the per-ride contract above SHALL be the thing it extends
