## ⚠ Read this first — the defect a build straight from the brief would have shipped

Surfaced rather than built around. **Neither of these reopens a decision**; both change what the
migration has to contain.

### 1. A `club_invited` notification for a PRIVATE club is unreadable by the rider it addresses

`notifications` SELECT carries a per-subject-column conjunct (`036` §3), read live off `pg_policies`
on DEV:

```
(club_id IS NULL)
  OR EXISTS (SELECT 1 FROM clubs scl WHERE scl.id = notifications.club_id)
  OR ((type = 'club_join_request_declined') AND private.club_takes_join_requests(club_id))
```

and `clubs` SELECT is `is_public OR owner_id = auth.uid() OR private.is_club_member(id)` — **no
invite arm, no block arm**. An invitee to a private club is not its owner and not a member, so the
`EXISTS` is false and the notification is **written and then never returned, for ever**, looking
correct to every reviewer and to any test that only checks the row was inserted. That is `085`'s
recorded trap, arriving on the exact surface this change exists to build.

**`089` already set the remedy and this change copies it**: a **type-scoped** third disjunct, so the
widening reaches one type and one predicate rather than every `club_id`-carrying row. This change
adds a fourth:

```
OR (type = 'club_invited' AND private.has_live_club_invite(club_id))
```

**Both policies move, not one.** The same predicate is the qual of `Notifications are readable only
by their recipient` (SELECT) **and** of `Riders mark only their own readable notifications read`
(UPDATE) — `md5(qual)` is `28ab04505c62f16147539f78b521a858` for both, on **DEV and PROD**. Moving
only the SELECT gives the invitee a notification they can read and can never mark read: a permanent
unread badge with nothing behind it that clears it.

### 2. `085`'s header states something about `club_members` that is no longer true

`085_club_join_requests.sql` justifies refusing an approval into an owner-block with *"club_members
SELECT carries no block predicate, so the two would then appear on each other's roster."* Measured
on DEV today, that policy is

```
(private.is_club_member(club_id) OR EXISTS (SELECT 1 FROM clubs c WHERE c.id = club_id AND c.is_public))
AND ((user_id = auth.uid()) OR NOT private.is_blocked(auth.uid(), user_id))
```

— it **does** carry one. **The rule `085` states is still right and this change keeps it**; only its
stated reason has expired. The surviving reason is larger than the roster: a membership admits a
rider to the club's threads, messages, rides and timeline, which is the shared space decision #2
exists to keep two blocked riders out of. Written down here because the next reader will otherwise
re-derive the rule from a false premise and may conclude it can be dropped.

## Why

**A private club's `Share club` row is a live defect, and it now has two callers.**
`ClubOptionsMenu` calls `shareAppLink(routes.club(clubId))` unconditionally; `clubs` SELECT refuses
that route to the non-member you sent it to, so the recipient gets "content unavailable". PD-356's
`openspec/changes/club-timeline-engagement/design.md` §Q1 — answered 2026-08-31, *the row shares the
CLUB, labelled `Share club`* — records this defect as open and, deliberately and annotated at the
site, adds a **second caller**: that row on the club thread screen, which inherits the same breakage
the moment the club is private. Its own words: *"this change is not allowed to ship a second caller
of it without saying so."*

**So the fix must be one shared component, not a branch copied into two menus.** Two call sites each
testing `is_public` is the shape where the next surface gets the branch wrong, or gets it right and
then drifts; and a third caller is likely, because every main screen now carries a ⋯ menu (PD-280).
The component and its contract are in `design.md` §The share row is one component with three callers.

**And beyond the defect: a private club cannot be filled.** Since `085` a rider can *find* a private
club and ask, but nobody inside it can *invite*. On its first day every private club has one member
and no way to get a second except by telling somebody, out of band, to go and search for it.

## The decisions, and what each one costs

Settled — enumerated with their reasoning, not reopened.

### 1. A public club gets NO tokened link, and that is a decision rather than a gap

`clubs` SELECT admits **every signed-in rider** to a public club, and `club_members` INSERT lets any
of them join it. So the plain URL — `routes.club(id)` — already carries the entire grant a token
could carry.

**A token there would be a capability surface with no capability behind it.** It would cost a row,
an expiry, a revoke, a use count, a claim RPC and a landing route, and buy a rider exactly the
access they already had by pasting the same club's URL. Worse, it would create a second, weaker way
of describing the same permission — and the day somebody narrows public-club visibility, there are
two mechanisms to reason about instead of one.

**The token exists only where it grants something the URL does not**, which is the private club.
Stated as a decision because the symmetry is tempting: two visibilities, two rows, two links looks
tidier than two visibilities and one link.

### 2. Private clubs get both mechanics: an in-app invite and a capability link

The in-app invite reaches a rider who is already on LetsRide and findable by username. The link
reaches the four people in a group chat who are not. They are different features with different
threat models and the product owner asked for both.

### 3. Who may invite, and who may mint — the authority is the approval authority

**Minting authority is exactly `private.is_club_admin_for`** — the club's `owner_id` union its
`club_members` rows with `role in ('owner','admin')`, `085`'s own definition, which is also the set
that may answer a join request.

The argument is not "admins do administrative things". It is that **any looser set defeats `085`.**
If an ordinary member could mint a link into a private club, a rider whose join request an admin
declined could get a link from a friendly member and be in — the decline would be reversible by
somebody with no authority to reverse it. The set that may admit a rider must be the set that may
refuse one.

**On a public club, an ordinary member may send an in-app invite**, because there it is a *pointer*
rather than a grant: the recipient could already open the club and join it. One table, one row
shape; what differs is what the row buys, and that is decided by the club's visibility at the moment
it is used rather than by a column on the row.

### 4. A link claim admits the rider directly — it does NOT go through `085`'s approval

**Decided by the product owner, 2026-08-31: the bypass is accepted, with one refinement.** Put to
them as "straight in" versus "into the approval queue", they answered:

> "Its also a bit weird that I open a link and all of a sudden I am in a club that I havent even may
> know for sure what is it about. So maybe the invitee gets the chance to browse the club and only
> then can click 'join club' on the bottom bar?"

So there is **no admin approval** — the tap admits directly — and the landing must read as *browsing
a club and deciding*, never as a token being redeemed. That makes two things load-bearing rather
than incidental, and both are requirements rather than design notes: the preview must let a rider
answer **"is this the club I was told about"** *before* anything is spent, and the token must be
spent by a **tap** and never by a render. `design.md` §The landing screen is the club's own preview
screen carries the shape.

**The defence for the bypass itself is in three parts.**

- **The approval step exists to gate a rider-initiated join.** `085`'s request is a stranger asking;
  the admin's decision is the club's consent. A link is the club **initiating** — an admin's
  affirmative act, given in advance to whoever they hand the token to. Requiring a second consent
  from the same authority that minted the token asks the club to approve its own invitation.
- **A request-only link would be the very thing decision 1 refuses.** Since `085`,
  `discoverable_private_clubs` returns **every** private club a rider is not already in, not blocked
  out of and does not own — so any signed-in rider can already find any private club and request to
  join it. A token whose only power is to write a `club_join_requests` row therefore grants nothing
  the app already grants for free; it is a deep link, not a capability. Building the token machinery
  for it would be a capability surface with no capability behind it, one section after we refused
  exactly that for public clubs.
- **The ride precedent is exact and it is the closer one.** `091`'s `claim_ride_invite_link` writes
  the `accepted` invite row and the `ride_members` row; nobody approves the claimer. This change is
  that shape with the club's membership row as the terminal write.

**What it costs, stated:** a leaked link is an open door into a private club until it expires or is
revoked, and every rider who walks through it is a member with no per-rider decision behind them.
Three things bound it: the **14-day ceiling**, the **revoke**, and — unlike rides — **`088`'s
`remove_club_member` actually exists**, so an admin can eject a rider a link admitted. That last one
is the material difference from `091`, which had to state that revoking ejects nobody and that
nothing in the schema could. Here something can.

**One gap that removal does NOT close, and it is named rather than discovered**: a removed rider who
still holds the token can walk straight back in, because nothing records the removal. The admin's
remedy is to revoke the link (and to block, which is decision #2's sledgehammer). **Filed as
PD-361**; nothing here builds it. See `design.md` §What removal does not do.

### 5. Expiry — an absolute **14 days** (decided), revoke, a derived use count, no max-uses cap

**`091`'s `least(departure, 14 days)` has no club analogue for its first argument**: a club has no
departure and therefore no natural death, which `share-a-ride-invite-link`'s own design.md names as
one of the two genuinely club-specific pieces. So the ceiling is absolute and it is the whole
control.

**Fourteen days, decided by the product owner 2026-08-31**, for `091`'s reason unchanged: two
weekends plus a slip, re-issuing is one tap, and a longer window stops being a bound. The shape — a
ceiling written by the database, re-checked at every use — is what must not change if the number
ever does.

**No max-uses ceiling**, on PD-293's precedent (`077` dropped the ride capacity because an invisible
cap is worse than none): the rider who hits it is a stranger who just installed the app, and the
message they get is indistinguishable from expiry and revoke.

**The use count is derived, never counted into a column** — the number of `club_members` rows
carrying the link's id. A counter drifts; a derived count cannot, and a rider who claims twice
produces no second row. It can go **down**, for two reasons: the rider leaves, or the rider blocks
an admin and drops out of that admin's block-dominated view of the roster. The surface says
`N joined`, never presents a ledger.

### 6. `club_invites` and `club_join_requests` are TWO tables

The most consequential structural call in the change; the full argument is `design.md` §One table or
two. The short form: they are **mirror images across the direction of the ask**, and it is the
policies that mirror — who may insert, who may answer, who may clear, and which party a refusal is
terminal against. A single table needs a `direction` branch inside every policy, inside the status
CHECK and inside both RPCs, which is `notifications_subject_shape`'s shape (a `case` with `else
false`) applied to access control rather than to column presence. And `club_join_requests` is
**applied and live on both projects**, so merging is a destructive rewrite of a live table's policy
set to buy tidiness.

## What a token buys — the narrowness proof

**This is the part to check first.** Possession of a live club token permits exactly two RPC calls:

| Holding a live token lets you | It does NOT let you |
|---|---|
| Call `club_invite_link_preview(token)` and receive **six named columns** of exactly one club | Read a `clubs` row through RLS — **this change adds no arm to `clubs` SELECT and does not touch `private.can_read_club`** |
| Call `claim_club_invite_link(token)` and join that one club | Read the roster, the threads, the messages, the club's rides, its timeline or its postcards, before the claim |
| | Learn anything without a session — both RPCs are granted to `authenticated` alone |
| | Learn anything without **both onboarding stamps** — the gate governs the preview as well as the claim |
| | Defeat a block, in either direction, with the minter or with the club's owner |
| | Learn the club's **description**, **cover**, **owner** or **age**, none of which are among the six |

After a claim the rider's reach is an ordinary `club_members` row and nothing else. **An admitted
claimer is byte-for-byte the same audience member as an approved join request** — already specified,
already asserted. The token is a way of reaching an existing grant, never a new one.

The in-app invite is narrower still: **a pending invitee reaches nothing at all.** The only policy
that moves for them is `notifications`, and the only thing it makes readable is the line telling
them they were invited. Everything they can see of the club — name, avatar, location, member count —
they could already see through `085`'s `discoverable_private_clubs`, which returns every private club
they are not in and not blocked out of. That equivalence is asserted rather than asserted-by-prose.

## What Changes

**One migration, `093`.** `092` is `club-timeline-engagement`'s and `094`/`095` are two further
concurrent changes'; task 0.3 re-derives the number rather than trusting this sentence.

**It is additive in schema and NOT inert**, for two reasons, and both put it under `036`'s
hand-exercise gate:

- it **replaces two live policies** on `notifications`, a table every screen reads; and
- `private.notify_club_joined` fires `after insert on club_members` with no `WHEN` clause, so from
  the moment `093` applies it runs inside `private.join_club_from_invite` and a raise there takes a
  rider's accept or claim down with it — `085`'s own hazard, one path over.

**Its ordering is `089`'s, not `069`'s**: additive in schema, ordered by the **client**. Two
notification types arrive, and `notificationCopy` and `NotificationsListItem`'s `describe` are
exhaustive switches — one `club_invited` row landing while an older bundle is serving takes that
rider's notifications screen down. So the bundle serves first and `093` applies after.

### New

- **`public.club_invites`** — `id`, `club_id`, `invitee_id`, `inviter_id`, `status`, `created_at`,
  `responded_at`. `unique (club_id, invitee_id)`, `check (invitee_id <> inviter_id)`, the `is not
  distinct from` response coupling (`073`'s correction), and **`status in ('pending','declined')` —
  two values, not three.** `085`'s rule rather than `083`'s: **accepting DELETES the row** and the
  `club_members` row becomes the record, because for a club the membership *is* the audience and a
  surviving `accepted` row beside the unique key would make a club a rider once left un-invitable.
- **`public.club_invite_links`** — `id`, `club_id`, `created_by`, `token`, `expires_at`,
  `created_at`, `revoked_at`. `token` is 128 bits of `extensions.gen_random_bytes(16)` as 32
  lowercase hex, **server-owned by the absent column grant** rather than by its default, with a
  `check (token ~ '^[0-9a-f]{32}$')` and a `unique`.
  **`expires_at` is a plain column DEFAULT here, not `091`'s BEFORE INSERT trigger** — the value is
  `now() + interval '14 days'` and reads no other table, so the trigger `091` needed has nothing to
  do. It is server-owned the same way: the grant does not name the column.
- **`public.club_members.invite_link_id`** — nullable FK to `club_invite_links(id)`, **`on delete
  set null`**, holding no grant to any client role for INSERT or UPDATE (measured: `authenticated`'s
  INSERT grant is per column over `club_id, role, user_id`, so a new column is unwritable by
  default). Provenance only, and the use count is derived from it. **No policy, trigger or read
  predicate may branch on it** — `091`'s `link_id` rule verbatim, with its assertion.
- **Two notification types** — `club_invited` and `club_invite_declined`, both carrying `club_id`
  alone, which is `club_joined`'s shape, so `036` §3's per-column conjuncts already cover them.
  **There is deliberately no `club_invite_accepted`**: `private.notify_club_joined` already fans
  `club_joined` out to the owner and admins on the `club_members` INSERT the accept performs, and a
  second row would tell the same people the same thing. `091` made the identical call about
  `ride_joined`.
- **Fifteen `private` helpers and six `public` RPCs**, enumerated in `design.md` §The function
  inventory. The public six are `accept_club_invite`, `decline_club_invite`, `my_live_club_invites`,
  `club_invite_link_preview`, `claim_club_invite_link` and `revoke_club_invite_link`.
- **A public landing route, `/clubs/join`**, and — as `091` learned — that is **two guard edits, not
  one**: `PUBLIC_PATHS` *and* `needsOnboardingState()`, because the latter's first line is
  `if (!isPublicPath(pathname)) return true`. One edit alone parks a newly signed-up rider on a
  screen whose only button raises `check_violation` for ever.

### Changed

- **`notifications` SELECT and UPDATE** gain the type-scoped `club_invited` disjunct — see the
  warning above. **The RLS suite pins that qual by equality; here the pin is SUPPOSED to move**,
  which is the opposite of `091`, where a moved pin means the change is wrong. Task 5.2 says which.
- **Both `notifications` CHECK constraints**, from eleven types to thirteen, moving together.
  `036`'s reason: the `case` has an `else false` and a type added to the flat list but not the shape
  is refused rather than silently admitted.
- **`ClubOptionsMenu`'s single unconditional `Share club` row** becomes one shared component with
  three states, mounted by both existing callers — see §Why and `design.md`.
- **`public.enforce_participation_gate()`'s comment**, restamped and its enumeration extended, per
  `028`/`033`. It is the `data` agent's first read through `list_tables` and no edit to `CLAUDE.md`
  reaches it.

### Explicitly NOT in this change

- **A token for a public club.** Decision 1.
- **Any arm on `clubs` SELECT, and any change to `private.can_read_club` or to
  `discoverable_private_clubs`.** `085`'s reasoning holds unchanged: an arm on `clubs` SELECT also
  moves `016`'s two `storage.objects` policies and `036` §3's notifications conjunct, neither of
  which any migration would mention. The suite pins both by equality and **a failure there means
  this change is wrong.**
- **Any change to `club_join_requests`' policies or to `085`'s two RPCs.** The two mechanisms are
  made deterministic by refusing an invite while a request stands and by the claim clearing a
  request it has made moot — both of which live in `093`'s own objects.
- **Making a removal stick against a live token.** Named as a gap and **filed as its own story,
  PD-361**, on PD-351's precedent. Nothing is built for it here, and the decision it needs first —
  what a removal *records* — is that story's, not this one's.
- **A retraction trigger for `club_invited`.** `090` removed the ride one for a measured reason —
  with the retraction, withdraw-and-re-send re-notifies without limit, because the deleted row
  never collides with `notifications_event_key`. Not repeating it is a decision, and it comes with
  `090`'s accepted cost: a withdrawn invite leaves a notification standing, which must degrade to
  plain text rather than to a dead control.
- **Universal links.** The link opens the **web** app until PD-205 ships; a rider with the app
  installed who taps it in WhatsApp gets a browser, signs in there and claims there. The claim is
  durable — the `club_members` row is in the database — so the club is on their clubs list when they
  next open the shell. Nothing is lost.
- **Push delivery.** `deliver-push-notifications` owns that surface; this change adds two types and
  no delivery.
- **Auto-claiming on session establishment.** Refused permanently and asserted against — `091`'s
  rule, and it is *worse* here, because the wrongly-admitted rider joins a private club rather than
  a single ride.

## Capabilities

### New Capabilities

- `club-invites`: what an in-app club invite is, who may send one on a public club and on a private
  one, what it grants (nothing, until it is accepted), what the invitee may read, who may answer,
  withdraw and clear it, what happens when the inviter's authority ends, what a decline means and
  who it is terminal against, and every one of the eight non-answerable cases — stated per role:
  owner, admin, member, invitee, non-member, blocked rider in either direction, and signed-out
  visitor.
- `club-invite-links`: what a club token is, what holding one grants and never grants, who mints,
  lists and revokes one, when it dies, what the six preview columns are, what a claim writes, and
  what every dead state renders — for every role that can hold a URL.

### Modified Capabilities

- `notifications`: the standing requirement that *a notification SHALL be dropped by the database
  when its subject is no longer visible to its recipient* is exactly what makes a private-club
  invite unreadable. The type-scoped exception `089` introduced is now a **pattern with two
  instances**, and the requirement has to say when it is permitted, or the next type widens the club
  conjunct outright.
- `event-fanout-integrity`: two new fan-outs, one of which addresses a recipient who **cannot read
  the subject through the ordinary conjunct** — the standing "never write a row the read policy can
  never return" requirement is satisfied by moving the policy rather than by dropping the row, and
  that resolution is not currently written down.
- `database-enforced-integrity`: this change adds the first grant in the schema whose validity is
  **re-derived at every use rather than fixed at creation** — an invite minted by an admin who is
  later demoted, or into a club that later goes private, must stop working. That is a new class of
  rule and it belongs beside the gate-count requirement it composes with.
- `club-join-requests`: the two mechanisms meet, and one must win deterministically. That capability
  is **not yet in `openspec/specs/`** — `show-private-clubs-and-request-to-join` and
  `manage-club-riders` are both still active — so the delta carries the ordering banner.
- `client-cache-invalidation`: an accept and a claim each move keys across two domains, and the
  claimer **arrives at the club** immediately afterwards. A claim additionally has no prior screen to
  invalidate from, because the rider may have had no session when the read was cached.
- `client-session-storage`: a **second** capability token now exists on the device, of a different
  kind and the same 32-hex shape. The standing rules — sign-out destroys every local trace, a
  signed-out visitor reaches no data — need to say that two stashes never spend each other.

## Impact

**Database** — one migration (`093`) and assertions in `supabase/tests/rls_test.sql`. Re-derive the
suite size with `PGPASSWORD=postgres npm test 2>&1 | grep -c "NOTICE:  ok"` and **reconcile by label
set, never by count** — a count cannot tell a rename from a loss.

**Security advisors** — **+6** `authenticated_security_definer_function_executable` WARNs, one per
new `public` `security definer` function. **The fifteen `private` helpers add none**, PostgREST not
publishing that schema — `085` is the worked example, where eleven new functions moved the count by
three. Task 0.5 records the **before** number off `get_advisors(security)`; the expected delta is
+6 and an unexpected advisor means something was created in `public` that belongs in `private`.

**Participation gate** — **+2** triggers, one per new table. **17 on DEV and 17 on PROD, measured
2026-08-31**; `092` takes it to 19 before this file, so the after-count depends on which of
`092`–`095` has applied. **Assert the delta and the two table names, never the absolute** —
`select count(*) from pg_trigger where tgname = 'enforce_participation_gate' and not tgisinternal;`

**`join_club_from_invite` is `078`'s case exactly.** A gate trigger cannot fire for a `security
definer` writer, because every gate trigger carries `when (current_user = 'authenticated')` and
`current_user` inside a definer body is the owner. The gate is therefore restated in that function's
body via `private.may_participate_for(rider)` — **never `may_participate()`**, which is
caller-relative and would answer for the accepting admin on the claim path. Do **not** add a
compensating trigger to `club_members`; `078.9` asserts that absence precisely because it would
raise the gate count while gating nothing.

**Reads** — `src/lib/data/club-invites.ts` and `src/lib/data/club-invite-links.ts` through
`resolveSupabase`. **Writes** — the two matching modules in `src/lib/actions/`, plain async
functions. No component calls `supabase.from()`.

**Cache** — five keys in `src/lib/query/keys.ts`, each with the docstring that file's convention
requires, plus a documented cross-domain invalidation from the accept and the claim.

**Validation** — `clubInviteTokenSchema` in `src/lib/validation/clubs.ts`, 32 lowercase hex. Zod
owns the **message**; the CHECK and the absent INSERT grant own the **guarantee**.

**Types** — `ClubInvite`, `ClubInviteLink`, `ClubInviteLinkPreview` and `ClubInviteClaim` in
`src/types/index.ts`; `NotificationType` gains two members.

**Design** — **no v2 frame exists for a club invite or its link section**, so those are assembled
from measured components (`ContextMenu`, `SectionHeader`, `Avatar`, `Button`, and `RideInvitePicker`
/ `RideInviteLinkSection` as built precedents) rather than invented and called measured; task 0.9's
first command is `npm run figma -- ls "*nvite*"`, read offline. **The landing screen is not in that
category and must not be designed at all**: it is `ClubPreviewScreen`, which `085` already built for
this exact rider, gaining one `action` slot and one `is_public` branch. Primary buttons are near-black
`Grey/100`, never green.

**Dependencies** — none added. Nine runtime dependencies before and after
(`node -p "Object.keys(require('./package.json').dependencies).length"`).

**Docs** — `CLAUDE.md`'s advisor table `+6`, its participation-gate paragraph `+2` tables, and its
