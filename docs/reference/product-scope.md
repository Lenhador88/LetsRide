## Product Scope (from Figma)

The built app covers a fraction of the design. **Four nav tabs — Home, Rides, Clubs,
Profile** — against the design's five: **Inbox was removed on 2026-08-07** (PD-100) rather than
shipped as the disabled stub it had been, because a tab that goes nowhere is an App Store
guideline 4.2 question and a disabled one still reads as broken. It returns with the Inbox epic.
**The design is not the code here, deliberately** — check the code first and Figma second:

```bash
sed -n '/const navItems/,/] as const/p' src/components/layout/Navbar.tsx | grep -c "href:"
```

**Scope the range before counting.** A bare `grep -c "href:"` on that file reads **9**: the four
nav rows, four `STICKY_ACTIONS` entries, and — the one that catches people twice — the `href:
string` in the `Record` type annotation declaring the map. Counting `Icon: ` instead returns the
right 4 today but is unguarded, because the file's own docstring already writes `MailboxIcon`
twice; scoping to the array cannot over-match from prose at all.

There is no "Friends" tab either, for a different reason: `013` dropped the `friendships`
table on 2026-08-04, and the route and components went earlier. The social graph is clubs
plus blocking.

It brings the app's **first public route that is not an auth screen or static copy**, `/rides/join?token=…`, and **decision #1 is still untouched**: the route is public so it can HOLD a credential through the auth round trip, never so it can show anything — a visitor with no session sees a generic sentence and two buttons and no ride data at all, because the preview RPC needs `auth.uid()` for its block and participation checks. The token is stashed in `sessionStorage` and the rider is returned to it after signing in or finishing the wizard; the claim is always a tap. **The route is in `PUBLIC_PATHS` and in `needsOnboardingState` both**, which is two edits rather than one and is the thing to preserve if it is ever refactored. **Revoke stops the link and ejects nobody**, because nothing in this app can remove a rider from a ride — PD-351 |
| **Clubs** — public/private, Overview/Rides/Members/Posts tabs | **Built 2026-08-05**, all of it v2. **`/clubs` is one screen as of `PD-258`** — the header's `Your clubs ⌄` dropdown is deleted, a tappable `Explore N clubs` strip sits between the header and the list, and a rider who has joined nothing gets the explore list rendered in place of an empty state, on the same route. `/clubs/explore` survives as its own route, now titled and reached with a back button. Both carry `List / Club` rows with the type chip, the rider collage and the club images; **the unread counter is Your clubs only** — `getExploreClubs` passes no unread argument, because `015` refuses a watermark for a club the rider has not joined and the design puts `Join club` in the slot the counter occupies. **`/clubs/detail` is a TIMELINE as of 2026-08-31 (PD-299 #4)** — one screen, top to bottom: the upcoming-rides scroller; the club's own line, the member rail, a `Threads` row carrying an aggregate unread mark, and its description; then the stream. **Every create is a sticky `Create` primary above the tab bar** (`ClubCreateBar`), in the slot `Create club` occupies on `/clubs`, opening a sheet of Postcard / Ride / Thread — so no section heading carries a `(+)`. The bar is member-only and therefore the screen's own rather than a `STICKY_ACTIONS` entry, which is keyed on pathname alone — so it approximates the frame's integrated bar (one component, one top stroke) by sitting flush against the nav bar with no border of its own, borrowing `.bottom-navbar` from `RideAttendanceBar` as a mechanism rather than as a precedent for the composition. It was four sub-pages until the 2026-08-18 merge and five stacked sections after it, and the merge is what made the sections the problem. **The Postcards carousel and the Threads section are gone** — a postcard is a full `PostcardCard` in the stream and a thread is a row in it, on the product owner's explicit choice over keeping either. **It is built from `Private club - Timeline` (`2043:10604`), which existed the whole time**; the identity band, the action layer, the thread row and the ride card are ours — the frame predates threads entirely, and its own ride row is a post-hoc *"went on a ride!"* rather than an announcement. **No migration and no new table**: the four sources (`club_threads.created_at`, `postcards.created_at`, `rides.created_at`, `club_members.joined_at`) all existed with unforgeable timestamps, and the merge is client-side over four RLS-filtered reads rather than a definer union, so each row stays filtered by the policy that owns it. **"Announcements" is the product owner's name for the derived event row, not a record** — there is no announcements table and an admin-composed one is out of scope. **The stream draws four row shapes** (PD-355, 2026-08-31): a postcard as a full `PostcardCard`, a ride as its `RideCard` under an `X planned a ride` label, a thread — created or replied to — as a 72px row with the thread glyph, its participants' faces and its reply count, and joins plus the club's founding as the frame's 44px `Grey/10` run. The reply count and the faces come off the same message window the reply events read, so on a busy club the count is a floor and the row says `12+` rather than asserting a total it cannot know. **The stream carries REPLIES as well as thread creations**, one entry per recently-active thread at the instant of its newest message — so a thread begun three weeks ago and busy this morning surfaces at the top while its creation entry stays where it is true. It needs no migration: what the client cannot ask for is a `last_message_at` aggregate, not a bounded window of `club_messages`, which `081` grants and its policy scopes to the club. A **non-member of a public club gets no timeline and no reads issued**: rides and the roster would come back populated while threads and postcards would not, so the stream would say the club is dead. Both public-club epics are still On hold. `/clubs/new` is a client page with an image upload (`016`). **Threads shipped `PD-307`**, named Discussions until `PD-313` renamed it — the word is worth carrying because the *ride* has a Chat and this is deliberately not that — titled threads on a club, `034`'s chat pattern with the audience swapped to club membership: a section on `/clubs/detail`, `/clubs/detail/threads`, `/clubs/detail/thread` and `/clubs/detail/threads/new`, with a per-thread unread dot and the app's second Realtime subscription. **Composition is ours** — there is no v2 Threads frame, so `Ride - Chat` and `Inbox - Chats` are the measured sources. Three schema facts shape the screens and are not defects: nothing is editable (neither content table has an UPDATE policy or grant), message deletion is `delete_own_club_message` and never a `.delete()`, and a blocked pair may both post in one thread and each sees only their own. **Pinning is NOT built** — `081` adds no column for it, so the Welcome club's greeting thread sorts by creation like any other and can be buried; PD-299 asked for a pinned one, and it waits on a column rather than on the Admin role, which `088` shipped. The Timeline's **activity feed shipped 2026-08-31** and the claim that it needed a table nothing writes was wrong — joins carry `joined_at` and needed no schema at all. **Leaves still have no backing row and never will**, a leave being a DELETE, so there is no "a rider left" entry and cannot be one under this design. **Member invitations shipped `PD-360`/`093`** and this line used to say they were what remained unbuilt — check rather than trust either reading: `grep -rn "accept_club_invite\|claim_club_invite_link" src/lib/actions/`, which finds the picker's invite path and the link claim. **The Admin role itself is no longer the blocker and this line said it was**: `088` (PD-326) shipped `promote_club_member` and `demote_club_admin`, so `club_members.role` — `admin` since `001` — has had a writer since 2026-08-30. Check rather than trust it: `grep -rn "promote_club_member" supabase/migrations/ src/`. Note the flow has two Explore designs — the row list is `Explore clubs — Done`, the 2-up grid is `Explore clubs v2 — On hold`. **Create club has no v2 design** — that epic reads To do, so its composition is ours. **Edit and delete shipped `PD-101`**: `/clubs/detail/edit`, owner-only, reached from the header; delete goes through `delete_owned_club` (`043`) with a blast-radius confirmation, never a bare `.delete()`. **Introductions shipped `PD-365`/`097`**: a rider who holds a membership with no introduction yet is offered a dismissible sheet on the club detail — driven by that STATE and never by the Join button, because six write paths create a membership and the one a button would reach worst is onboarding's auto-join. Posting writes a marked thread through `introduce_to_club`; the rider's join row on the timeline then carries a comment glyph and count that opens it, PD-356's `Say welcome` overflow is gone, and thread rows show the same glyph and number instead of `N replies`. The Welcome club and a club's own owner are exempt, in the RPC as well as in the UI. The sheet has **no v2 frame** — see `docs/FIGMA-FIDELITY-TODO.md` §Club detail. **Back from a thread lands on the club detail AT THAT ROW** (`PD-366`), header arrow and swipe-back alike, through a bounded `row` parameter carrying the timeline's own ordering key; absent or unresolvable falls back to the thread list, which is what a notification tap and a shared URL both produce. **Two notification changes landed with them**: a reply or a wave on a club thread now tells its author (`PD-367`/`098`, the app's first fan-out on a `club_messages` insert) — **though the wave half is unreachable from the app since `PD-372`**, which made the announcement row the club timeline's only waveable row and retired the thread wave's whole client path; the trigger, the table and the `club_thread_waved` rows already delivered are all still there, and a join now tells **every member** rather than only the owner and admins (`PD-368`/`099`) — with the Welcome club still telling nobody, which is what keeps the second from addressing every rider with the entire signup stream |

**Blocking is a schema concern, not a feature.** A blocked user must disappear from feeds,
chat, search, and ride crews simultaneously. It belongs in RLS policies, and every review
must check it.

Maps are a **static thumbnail plus a Google Maps deeplink** — no Mapbox, no turn-by-turn,
no route rendering. Do not add a mapping SDK.
