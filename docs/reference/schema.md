# Schema — the per-table contract

Every row here is a *rule*, not a description: the grant lists, the cascade behaviour and the
audience predicates are what the RLS suite asserts. Re-derive a grant list from
`information_schema.column_privileges` scoped to `grantee = 'authenticated'` rather than reading
it here.

**Schema (key tables):**

| Table | Purpose |
|---|---|
| `profiles` | One per auth user. PK = auth user UUID. Has `username`, `bio`, `bike_model`, `location`, `avatar_path`, `cover_image_path`. `avatar_url` is **gone — `024`, applied 2026-08-05** after the code repair deployed. `014` had kept it as a fallback rather than dropping it unverified; the verification came back 0 non-NULL on both tables. The name survives in `src/` as a *field on what `lib/data/` returns*, holding the signed URL — never a column. The two `*_path` columns are Storage object paths under `avatars/<uid>/` and `covers/<uid>/`, each pinned to its owner by a CHECK on the row's own `id`. Render them through `resolveAvatarUrls` / `signImagePaths`, never directly. **`username` stores the case the rider typed and is unique case-INSENSITIVELY** (`056`): `Pedro` renders as `Pedro`, while `pedro`, `PEDRO` and `PeDrO` are unavailable to everyone else, because `profiles_username_lower_key` is a unique index on `lower(username)` and `profiles_username_format` is `^[A-Za-z0-9_]{3,25}$` (`056` set the charset, `057` the 25). Read availability through `username_exists(text)` and never through `.eq('username', …)` (case-sensitive) or `.ilike()` (LIKE treats `_` as a wildcard and the charset allows underscores). **`username` is durable: once it holds a value, `authenticated` cannot return it to NULL** (`038`). The rule is **"once set, never unset", not "once onboarded"**, so a rider mid-wizard cannot free a taken name either; a rename is still permitted, unbuilt and unsurfaced rather than decided. **`authenticated` holds no DELETE grant (`042`)** — deleting your own row reaches the same invisibility `038` closed, by a different door, and until `042` it was refused only by the *absence of a DELETE policy*, so any future DELETE policy added for an unrelated reason would have reopened it silently. The row is still reaped by the cascade from `auth.users`, which is how account deletion removes it (`029`–`032`) and which consults no table grant at all. |
| `rides` | Rides with `organizer_id → profiles`, optional `club_id → clubs`. The organizer FK is `ON DELETE CASCADE`, so **a ride is cancelled by its organizer's account deletion** — deliberate (a ride is one person's plan), and the crew is not notified because there is nothing to notify them with. `club_id` is `ON DELETE SET NULL`, which `029` treats as a trap rather than a default: a private club's ride left with `club_id` NULL and `is_public` false is visible only to its organizer while its `ride_members` rows survive, so the transfer function deletes a club's rides with the club instead. **`max_riders` stopped being decorative in `063`** — `018` bounded the value (1..999 or NULL) and said in its own header that it bounded nothing else; `ride_members`' trigger is what counts a crew against it now, and the `ride_members` row below carries the whole rule. **Grants are per column as of `045`** — `insert` over ten columns, `update` over eight; `created_at` is server-owned (neither verb), and `id` and `organizer_id` are insertable but **not** updatable, so a hand-off is refused by the grant as well as by the UPDATE `with check`. **There is no `updated_at` column**, which is a known gap rather than a decision now that `updateRide` ships. Re-derive the lists from `information_schema.column_privileges` scoped to `grantee = 'authenticated'`. **`051` adds five nullable tile columns** — `latitude`, `longitude`, `geocode_confidence`, `map_card_path`, `map_detail_path`. NULL is the **normal** state and the designed fallback, not an error: every ride that existed when `051` applied has them NULL and there is no backfill, because the render runs under the organizer's own JWT and nothing is entitled to render a ride it does not organise. A ride gets its tile the next time its organizer edits it. **`059`: a ride created in the `clubs.is_default` club notifies NOBODY.** `rides` INSERT is `club_id is null or private.is_club_member(club_id)`, so after `058` every rider may create a ride in the welcome club, and `036` §7.5's member fan-out would have written one `notifications` row per rider in the app, inside that rider's own INSERT, repeatable at will. The ride itself is unaffected and still visible to every member. Three CHECKs coupled to them, and the middle one is one-directional on purpose: a coordinate needs a confidence at or above the floor, a tile path needs a coordinate, but a coordinate **may** exist without a path — a successful geocode followed by a failed render is a real end state. Both path columns are pinned to `'ride-maps/' || organizer_id || '/%'`. **The grant is per-column since `045`**, so `051` grants UPDATE on the five explicitly; the proposal's premise that `rides` was table-level went stale a day before the build and would have failed every column write with `42501`. |
| `ride_members` | `(ride_id, user_id)` composite PK. `status`: `going` \| `maybe`. **Capped at `rides.max_riders` since `063`**, by **`private.enforce_ride_capacity()`** — a `BEFORE INSERT OR UPDATE` trigger, and the first thing in this schema to count a child table against a parent column. It is in `private`, like `notify_ride_joined` on this same table: PostgREST routes only to `public`, so the schema is what keeps it off the API surface and the revoke is the second lock rather than the only one. Five properties are counter-intuitive and each is load-bearing. It is a **join gate, not an invariant**: an organizer may lower a cap below the current crew, nobody is evicted, and an over-subscribed ride is a legal state — what the lowered cap buys is that nobody else gets on. It counts **rows of both statuses**, because "on this ride" already means "holds a row here, `going` or `maybe`" everywhere else (`private.is_ride_crew`, the chat audience, `036`/`055`/`060`'s fan-out). It is **`security definer` of necessity**, not convenience — `009` put `private.is_blocked` on this table's own SELECT policy, so an invoker-rights count is short by exactly the caller's blocks. **Two riders are exempt from the count, and both exemptions are load-bearing.** Anyone **already holding a row** takes no new seat — an `EXISTS` probe, *not* a count excluding `new.user_id`, which is the form this build proved wrong: it is enough on a ride exactly at its cap and refuses an existing member on an over-subscribed one, so a lowered cap would have frozen the crew it just promised not to evict. And the **ride's organizer**, who is on their own ride with or without a row (`getRide` renders a host holding none as `going`) — **this is the only way a WRITE HERE can push a crew past `max_riders`, and it adds at most one row, only when the organizer's row is written last, which `createRide` never does.** It is not a bound on crew size: lowering a cap exceeds `max_riders` by an unbounded amount, per the join gate above, so `crew <= max_riders + 1` is not an invariant and nothing should be built on it. It fires on UPDATE as well as INSERT because `048` grants UPDATE on `ride_id`, so a seat can be moved. `max_riders` NULL is no cap, which is what most rides carry. **Grants are per column as of `048`** — `insert` and `update` both over `(ride_id, user_id, status)`; `joined_at` is server-owned (neither verb), because `getRideCrew` orders on it ASC and caps at 200 with no pagination, so a back-dated value bought a place inside the truncation window ahead of genuine crew. All three UPDATE columns are **required, not tidy**: `setRideAttendance` is an upsert and PostgREST's `ON CONFLICT DO UPDATE` SET list carries every payload column *including both conflict columns*, so granting `status` alone fails every repeat RSVP with 42501. Re-derive from `information_schema.column_privileges` scoped to `grantee = 'authenticated'`. |
| `clubs` | Clubs with `owner_id → profiles`. **A club outlives its owner as of `029`.** The FK is `ON DELETE CASCADE` and `postcards.club_id → clubs` cascades behind it, so deleting an owner would destroy every postcard every *other* member ever posted there — `009` reasoned that link out correctly for a club deleted *by* its owner and never considered it arriving as a side effect of a third party's erasure. `private.transfer_owned_clubs` hands the club to its longest-tenured remaining admin, else member, and only deletes it when nobody is left. Reached through `031`'s `service_role`-only wrapper, never by a client. **An owner deletes their OWN club through `public.delete_owned_club(p_club_id uuid)` (`043`), never a bare `.delete()`**: the `rides` DELETE policy is `auth.uid() = organizer_id` with no club-owner arm, so a client delete leaves every private ride in the club detached by `SET NULL`, visible to its organizer alone, with its crew list and chat unreadable — and for a private club that is every ride. The RPC is `security definer`, re-checks `owner_id = auth.uid()` in its own body (RLS does not apply inside it), deletes the club's `is_public = false` rides with the club, and returns the club's own Storage object paths so the caller can delete the bytes. Cascade-deleted postcards' images belong to other riders and are permanently orphaned — `PD-94`. **Grants are per column as of `045`** — `insert` over seven columns, `update` over five; `created_at` is server-owned (neither verb), which matters more here than on `rides` because `getClubsToExplore` **sorts on it**, so while it was writable an owner could float their club to the top of Explore permanently. `id` and `owner_id` are insertable but **not** updatable, so a hand-off is refused by the grant as well as by the UPDATE `with check`. **There is no `updated_at` column** — the same known gap `rides` has. **The club audience predicate is `private.is_club_member(club_id)` and it is NOT a membership-only test as of `054`**: it is true for a rider holding a `club_members` row **or** named by `clubs.owner_id`, so a club's owner reaches their own club exactly as a member does whether or not that row exists. Ten policies across `rides`, `postcards`, `club_members`, `feed_reads` and `clubs` share it — re-derive with `select tablename, policyname, cmd from pg_policies where (coalesce(qual,'')||coalesce(with_check,'')) like '%is_club_member%'` — and a further set inherits it transitively through an RLS-filtered `EXISTS`, **including two `storage.objects` SELECT policies, so the reach extends to postcard image bytes and ride map tiles**. Before `054` the owner arm existed on `clubs` SELECT alone, so an owner holding no membership row saw their club and none of its rides, postcards or roster, and could not create a ride in it either. Two things the arm does **not** do: it never steps past a block (every occurrence is dominated by a `private.is_blocked` conjunct, the only escaping disjuncts being self-identity, which `blocks_no_self_block` makes safe), and it confers no moderation — `rides` writes stay `organizer_id`-keyed, `postcards` UPDATE `author_id`-keyed, `club_members` DELETE `auth.uid() = user_id`. It is also **caller-relative** — it resolves `auth.uid()` — so it must never compute a notification fan-out recipient set (`036` trap (c)). **`060` split the body out into `private.is_club_member_for(candidate, target_club_id)` and made this a wrapper over it**, so the same rule now has a subject-taking reading a fan-out CAN use, with one body behind both and no second copy to drift. That is what lets `ride_created_in_club` union `clubs.owner_id` into its recipients — via `private.can_read_ride(candidate, ride)`, which measures the read rather than asserting it — so an ownerless owner **is** now notified of rides in their own club, where `036` §7.5 withheld it. Neither new function is executable by any client role: both take a subject, so a rider holding EXECUTE would have a block oracle and a private-club membership oracle. **`058` adds `is_default`: the welcome club every rider joins the moment they complete onboarding.** At most one row may carry it (`clubs_one_default_club`, a partial unique index) and it must be public (`clubs_default_club_is_public`). `authenticated` holds **SELECT and neither write verb**, and that asymmetry is the security boundary rather than tidiness: `clubs` UPDATE's policy already lets an owner write their own row, so the column grant is the only thing between a rider and pointing every future signup at a club of theirs. **Which club carries it is data, not schema** — `Welcome club` on PROD, `Welcome club (dev)` on DEV, nothing on the RLS suite's scratch database — so read it (`select id, name from clubs where is_default`) rather than expecting an id in the migration, and expect NONE to be a working state: `complete_onboarding` joins nobody and onboarding is unaffected. **`058` changes neither grant count above** — `insert` is still over seven columns and `update` still over five, because `is_default` gets neither. **`059` makes the default club undeletable through `delete_owned_club`** (42501, the same refusal shape), because `029`'s succession can hand that club to an ordinary rider — it always has members now, so it never reaches the "nobody left, delete it" arm — and one tap would switch auto-join off for every future rider. Unflag it and it deletes normally. The inherited rename and imagery rights are a KNOWN GAP, reachable only by the welcome club's owner deleting their own account. **Since `066` a club carries its OWN location** — `location_name`, `location_place_id`, `latitude`, `longitude` (PD-259), filled from a picked `public.places` row and **never from the creator's profile**: product owner, *"the club location is not the location of the rider who created it."* All four move together or none does (`clubs_location_coupling`), NULL is the normal state, and there is deliberately **no foreign key to `places`** — that index is reloaded wholesale, so a FK would either block every reload or silently wipe every club's location on one. Read `location_place_id` as provenance, never as a join key: it can dangle and nothing will say so. The grants are ADDITIVE on top of `045`'s allowlist, so `created_at` and `is_default` stay unwritable. No new policy: the columns live on `clubs`, so `001`'s SELECT policy is the whole answer and a private club's location is visible to its members alone. |
| `club_members` | `(club_id, user_id)` composite PK. `role`: `owner` \| `admin` \| `member`. **Grants are per column as of `048`** — `insert` and `update` both over `(club_id, user_id, role)`; `joined_at` is server-owned (neither verb), because the roster sorts on it ASC and caps at 200 with no pagination. **The UPDATE grant is dead today** — there is no UPDATE policy on this table at all, which is what `036` §7.6 relies on for "nobody can promote an admin" — and it is narrowed anyway so a future member-promotion policy cannot inherit `joined_at` for free. Re-derive from `information_schema.column_privileges` scoped to `grantee = 'authenticated'`. **Since `058` this table has a writer no rider triggers**: `complete_onboarding()` inserts a `member` row here for the `clubs.is_default` club on the transition into completion. It runs as the function owner, so neither the INSERT policy nor `enforce_participation_gate` applies — and it is wrapped in a `when others` block, because a raise there would roll back the completion stamp in the same transaction and strand the rider in a wizard decision #5 gives no way out of. `private.notify_club_joined()` returns early for that club, or its owner would receive one notification per signup for ever. The rider can still leave: the DELETE policy is unchanged. **The roster is no longer opt-in**, so the 200-row cap above now describes a screen that can only ever show the 200 earliest members of a club containing every rider — and `members_count` on that club's card is the app's onboarded-rider count, visible to every signed-in rider. |
| ~~`friendships`~~ | **Dropped by `013`, applied 2026-08-04.** Gone from the schema and from `src/`. A v1 leftover; the design has no friendship concept. Listed here only so its absence is not mistaken for an oversight. |
| `postcards` | The photo feed / home screen. `author_id → profiles`, optional `club_id → clubs`, optional `ride_id → rides` (`041`). **`club_id` IS the audience** — NULL means the app-wide feed, set means that club's members. There is deliberately no `is_public` flag. **`ride_id` is a TAG, not a second audience** — the SELECT policy does not mention it, so nulling it changes who can see the postcard by exactly nothing, which is the property that keeps it a tag. Tagging needs the ride visible to the caller **and** `private.is_ride_crew`; neither alone, because a FK is validated with RLS bypassed and a `ride_members` row outlives blocking the organizer. `authenticated` holds no UPDATE grant on it, so a tag is set once at insert — that, not a policy, is what refuses a retag. **And as of `062` it holds no SELECT grant on it either**: the raw uuid is comparable, so a viewer who can resolve neither the ride nor its crew could still group postcards by it, and a select list could not close that because the browser queries PostgREST directly. The Journal filters through `public.ride_journal_postcard_ids(ride uuid)` instead — `security definer`, in `public` so PostgREST can route to it, returning **ids only** so the rows still come back through the ordinary RLS-governed read. Postgres checks a column privilege to FILTER as well as to return, which is why the grant and the Journal wanted the identical privilege and why closing one needed the other moved (PD-166). `image_path` is a Storage object path, never a URL, and must sit under `postcards/<your uid>/`. **`created_at` and `updated_at` are SERVER-OWNED as of `044`** — `authenticated` holds SELECT and neither INSERT nor UPDATE on either, so the only value they can ever take is `default now()`. `created_at` is the home feed's sort key *and* its pagination cursor, so while it was writable an author could pin their own postcard to the top of every feed permanently (PD-163); a `default` is the value and the grant is the guarantee, because a default applies only when the column is omitted. All three verbs are now per column: `insert (id, author_id, club_id, image_path, caption, ride_id)`, `update (club_id, image_path, caption)` and — since `062` — `select (id, author_id, club_id, image_path, caption, created_at, updated_at)` — re-derive with `information_schema.column_privileges` scoped to `grantee = 'authenticated'` rather than reading this list. A per-column SELECT grant means **`select('*')` on this table is `42501` for every rider**, and a column added here is unreadable by the app until it is added to that list — the standing cost `025` first took on for `profiles`. **`author_id` and `id` lost UPDATE in `046`**, which is `045`'s rule applied to all three owner-bearing tables: **no ownership column on `postcards`, `rides` or `clubs` holds an UPDATE grant, and all three stay INSERTable** — you may declare yourself the author of a new row and may never reassign an existing one. `club_id` deliberately keeps UPDATE, because the audience is meant to be changeable and `041`'s `with check` conjunct is what guards it. **`064` adds five capture columns — `taken_at`, `taken_at_offset_minutes`, `taken_latitude`, `taken_longitude`, `taken_location_precision` — and they are INSERT-ONLY**: the grant lists become `insert (…, taken_at, taken_at_offset_minutes, taken_latitude, taken_longitude, taken_location_precision)` and `select (…, the same five)`, while **UPDATE is not mentioned by that file at all**, which is what leaves it at `046`'s three columns and makes the columns unwritable after the insert. That absence is the mechanism, not an omission — touching UPDATE is how `044` and `046` reinstated each other's lists. **`taken_at` is the one column on this table the client MUST be able to write** (the value exists only in the rider's own file, so `044`'s take-the-grant-away instrument is unavailable) and it is the ride Journal's sort key, so it is BOUNDED instead: `postcards_taken_at_is_in_the_past` refuses a future value or anything before 1995 — the year `DateTimeOriginal` was specified, which is the floor that actually catches the epoch-0 and 1904 placeholders a 1900 floor lets through. `postcards_taken_at_offset_coupling` ties the instant to the offset it was resolved with, in both directions, so the camera's wall clock is always recoverable. **The location is a PRIVACY choice made before the request is built, not a display flag** — the composer offers Hide (default, nothing is sent), Region (rounded to 2 decimal places in the browser) and Precise, and `postcards_taken_location_coupling` plus `postcards_region_location_is_rounded` are what make the middle one true against a client this app does not control. There is no "stored but hidden" state and there must never be one: RLS is row-level, so the audience of these columns IS the audience of the postcard, and `062`'s reasoning arrives inverted here — a coordinate is comparable *and* externally resolvable, and unlike `ride_id` the mitigation cannot be a grant. NULL `taken_location_precision` means Hide **and** "no EXIF location", indistinguishable on purpose. |
| `postcard_likes` | `(postcard_id, user_id)` composite PK. No denormalised count — the correct count is per-viewer, so it is counted under RLS. |
| `blocks` | `(blocker_id, blocked_id)` composite PK. The row is **directional**, the effect **symmetric**. Never query it from a policy — go through `private.is_blocked(a, b)`, which is `security definer` because the blocked party cannot read the row. |
| `postcard_comments` | A comment has no audience of its own — it **inherits the postcard's**, expressed as an `EXISTS` against `postcards` rather than a second copy of the club predicate. No UPDATE policy and no UPDATE grant: editing is not designed. No denormalised count, same reason as likes. **`created_at` and `updated_at` are server-owned as of `048`** — `insert` is per column over `(id, postcard_id, author_id, body)` and there is still no UPDATE grant of any kind. The thread sorts `created_at` **ASC**, so while it was writable a commenter could pin their comment above the comments it replies to, permanently and for every viewer; `updated_at` came out for a different reason — the table has no UPDATE path at all and its trigger is BEFORE UPDATE only, so nothing ever stamped it on insert and a comment that can never be edited could be born claiming one. |
| `postcard_hides` | `(postcard_id, user_id)` composite PK. **Per-viewer and one-directional**, unlike `blocks` — a row only ever removes a postcard from its own `user_id`'s feed. It is an input to the `postcards` SELECT policy, so `club_id` is no longer the sole determinant of what a viewer sees. |
| `profile_countries` | `(user_id, country_code)` composite PK, added by `014`. Countries a rider says they have ridden in, **entered manually** — the derived reading is unbuildable, `rides` has no country or coordinates. `country_code` is ISO 3166-1 alpha-2 with a CHECK; there is no `countries` reference table, because the picker's list is the client's and nothing joins against it. SELECT inherits the profiles predicate via `EXISTS`, so blocking works without the word appearing in the policy. |
| `clubs` (media) | `016` adds `avatar_path` and `cover_image_path`, both Storage object paths under `club-avatars/<owner uid>/` and `club-covers/<owner uid>/`. Keyed on the **uploader**, not the club, because the object must land before the club row exists; a CHECK ties each path back to the row's `owner_id`. `avatar_url` was the legacy column nothing wrote; **`024` dropped it, applied 2026-08-05**. Five query sites embedded `clubs(id, name, avatar_url)`; the three that draw an image could only ever draw initials, because it was NULL on every row — see `CLUB_EMBED_COLUMNS`. |
| `feed_reads` | The unread model, added by `015`. A **read watermark per audience**, not a row per postcard seen: `(user_id, club_id)` where `club_id` NULL is the app-wide feed, mirroring `postcards.club_id`. Its uniqueness is `unique nulls not distinct` — a plain UNIQUE treats two NULLs as different and would insert a second app-wide row on every visit. Row count is bounded by **membership**, so it never grows with content; the rejected `postcard_views` alternative grows as riders × postcards. Read it through `club_unread_counts()`, a `security invoker` function, so blocks and hides are excluded by the same policies the feed obeys. Only club rows have a writer today — the app-wide row lands with the postcard filter tiles. |
| `postcard_reports` | `unique (reporter_id, postcard_id)` so a repeat report is a no-op rather than a brigading tool. **Write-only in practice**: no admin role exists, so only the reporter can read their own rows and nobody can triage. Recorded as a KNOWN GAP in `011`, not a feature. |
| `places` | The self-hosted location provider for ride meeting points, added by `037` — **the only table here that is not rider content**. Reference data extracted from Overture Maps and loaded out of band, so it has no owner column, no author, and the repo's first `using (true)` SELECT policy: every signed-in rider sees every row, which is correct precisely because the table references no person. `authenticated` holds **SELECT and nothing else** — the load runs as the table owner, which is what lets an operator write while nothing reachable through PostgREST can. Query it through `search_places(q, near_lat, near_lon)`, never an ad-hoc `ILIKE`: the function carries the guard that keeps a query off a sequential scan, and that guard is `term ~ '[[:alnum:]]{3}'` rather than a length check because `char_length(term) >= 3` accepts `'%%%%'`, which escapes to a pattern with no extractable trigram — measured at 1,443 ms, under the 8 s statement timeout and therefore silent. `039` widened what it matches to `name`, `brand`, `street` and `locality`, matched **per token and ANDed** against a generated `search_text` column, so `Jumbo Maastricht` reaches a Jumbo whose locality is Maastricht and adding a word always narrows. `postcode` stays out. Widening needs a ranking rule, so a place the query **names** outranks one it merely **locates** — `Amsterdam` puts the place called that above the thousands sitting there. The guard is unchanged and is already per-token, because an alphanumeric run of three cannot span whitespace. `039` also **drops** `places_name_trgm_idx` and `places_brand_trgm_idx` for one GIN index over `search_text`. **LOADED on BOTH projects — 736,538 rows each, 2026-08-11; DEV 163 MB heap + 175 MB indexes (`PD-195`), PROD 162 + 174** — and an empty index is indistinguishable from a working search that finds nothing, so count rather than assume. **The first real timings killed the synthetic ones**: `straat` matches 28.7% of the table and cost 11,458 ms against a predicted ~2,957, which is what `050`'s candidate cap exists for. **Loading it is `.github/workflows/places-load.yml`** (PD-173) — never a hand-written `insert`: `scripts/places/load.sql` is one transaction holding the `delete`, the `\copy`, the `analyze` and a detector that fails the load closed, so search is never observably empty and a short extract cannot land silently. **Attribution is SETTLED (2026-08-18, `PD-191`) and is not ODbL** — Overture publishes the Places theme under CDLA Permissive 2.0 and Apache 2.0, with no share-alike, and CDLA §3 exempts what an app renders ("Results") from carrying the licence text. A census of 527,725 rows — roughly 72% of the extract — names Overture, meta, Foursquare, Microsoft, AllThePlaces, PinMeTo, DAC and Krick and **zero** OpenStreetMap, so the "© OpenStreetMap contributors" credit this repo first assumed would have named a contributor that supplied nothing. The credit is paid once, on `/legal/attributions`; a screen rendering a place result owes nothing further. **One part is INFERRED rather than measured** — the per-source "special terms" table on Overture's attribution page is egress-blocked and unread; `scripts/places/README.md` §Attribution carries what that leaves open. `065` turns the same flag in the **table comment**, which is where a `list_tables` reader finds it. Geoapify's map tiles are a separate vendor with an unconditional OSM credit of their own (`PD-104`) — a different line on the same page, never merged into this one. |
| `ride_map_render_attempts` | The map tiles' **spend ledger**, added by `051` — one row per *attempted* vendor call, `ride_id` cascading from `rides`. It exists because the thing being bounded is a **vendor bill**, not the organizer's own data, and the organizer is precisely the party the limit is aimed at — a counter column on `rides` is resettable by whoever it bounds. `authenticated` holds **INSERT and SELECT only**: no UPDATE or DELETE grant and no such policy, so the only direction available to a caller is *up*, which is self-harm. `attempted_at` is written by a `BEFORE INSERT` trigger rather than a DEFAULT, so a client cannot backdate a row out of the rolling window. **The INSERT policy still carries the `< 10` comparison; what `052` moved out is the COUNT** — `private.ride_map_renders_in_window(ride_id) < 10`, where the helper is `security definer` in `private`. It had to move because a `count(*)` over the ledger inside the ledger's own policy raises `infinite recursion detected in policy` — structurally, whatever the inner query would have done — so no insert could ever have succeeded against `051` as applied. The count is therefore no longer RLS-scoped, which is the safe direction: narrowing the ledger's SELECT policy later can no longer silently widen the ceiling. It counts ATTEMPTS rather than successes: a geocode that returns nothing writes no columns, so a success-counter would never see the organizer retrying an address that will not resolve — who is exactly the rider the ceiling is for. |
| `ride_reads` | The **chat** unread model, added by `061` — `015`'s watermark transferred to a ride's conversation: `(user_id, ride_id)` with a `last_read_at`, bounded by crew membership rather than by message volume. **Two things it deliberately does NOT copy from `feed_reads`, and both are worth reading before assuming symmetry.** First, there is no `unique nulls not distinct` and there must not be: `ride_id` is NOT NULL, so a real **primary key** `(user_id, ride_id)` is available and doubles as the upsert's `on conflict` target — `015` needs the clause only because `club_id IS NULL` *means* the app-wide feed, and there is no app-wide ride. Second, **`last_read_at` is imposed by a `BEFORE INSERT OR UPDATE` trigger** (`public.stamp_ride_read()`), not trusted from the client: it is compared against `ride_messages.created_at`, which `034` §4b makes server-generated, and a comparison spanning a phone's clock and the database's is wrong in a way nothing logs. **`feed_reads` carries that defect today** — `markClubSeen` and `markFeedSeen` both send `new Date().toISOString()` — and `061` records it rather than inheriting it. **The write predicate is `034`'s full intersection**, on the INSERT and UPDATE `WITH CHECK`: `user_id = auth.uid()` **and** an `EXISTS` against `rides` under the caller's own RLS **and** `private.is_ride_crew(ride_id)`. `034`'s stated reason for that intersection does **not** transfer — a `WITH CHECK` grants no reads — and `061`'s comment says so; what transfers is `015` §2's, that without an audience predicate the foreign key is an existence oracle. The intersection is kept anyway so the watermark's audience is exactly the chat's, and because using the definer helper as a sole conjunct anywhere establishes by example that it is usable alone. The UPDATE `USING` is `user_id = auth.uid()` alone, deliberately. **No DELETE policy and no DELETE grant** — and note the reason is NOT `015` §2's, which says leaving a club cascades the row away: it does not, on either table. The FK is to `clubs` there and to `rides` here, so **leaving a crew leaves the watermark standing** and rejoining reuses it, which is correct. **Nobody but the row's owner may read it, and that is a refusal rather than an omission**: this app has no read receipts, and the SELECT policy is where that is enforced. **Retention is indefinite, and that is a decision rather than an omission** — a watermark lives as long as its ride, and dies with the ride or the rider through the two cascades and nothing else. Worth stating because this is the first table here whose rows are *behavioural* data about an identified person (when a named rider last looked at a named conversation) rather than their content or their membership, so it sets the precedent for the ones the roadmap will add. Nothing expires it, no job prunes it, and the alternative was never considered — say so rather than letting the next table inherit silence as approval. **No participation-gate trigger**, following `023`'s reason for `feed_reads` — a rider who has not consented cannot be crew, so the `WITH CHECK` already refuses them. Read the badge through `public.ride_has_unread(ride uuid)`, `security invoker` and **boolean rather than a count**, so blocks and ride visibility are excluded by the same policy the thread obeys and an `exists` needs none of the `limit 100` capping `015` required. It excludes the caller's own messages — `015` does not, which is a candidate defect there — and its `coalesce` has three arms (`last_read_at`, `ride_members.joined_at`, `rides.created_at`) where `015` has two: the organizer may hold no `ride_members` row at all (`034` §1), and with two arms the host is the one member of the crew whose dot never lights. |
| `ride_messages` | Per-ride group chat, added by `034`. **Its audience is an INTERSECTION and neither half alone is it** — riders who can see the ride (an `EXISTS` against `rides` under the caller's RLS) *and* who are on its crew (`private.is_ride_crew`: organizer, or any `ride_members` row of either status). Using the crew helper on its own is the trap this table already fell into once: it is `security definer`, so it steps past the block and private-club arms of the `rides` policy, and a `ride_members` row outlives both — an ex-club-member kept reading a private ride's chat. INSERT is granted **per column** so `created_at` cannot be client-written (a `default` only applies when the column is omitted, and ordering is the product here). No UPDATE policy and no UPDATE grant. In the `supabase_realtime` publication, which is what makes a subscription fire at all. |
