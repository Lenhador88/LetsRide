# Schema — the per-table contract

Every row here is a *rule*, not a description: the grant lists, the cascade behaviour and the
audience predicates are what the RLS suite asserts. Re-derive a grant list from
`information_schema.column_privileges` scoped to `grantee = 'authenticated'` rather than reading
it here.

**Schema (key tables):**

| Table | Purpose |
|---|---|
| `profiles` | One per auth user. PK = auth user UUID. Has `username`, `bio`, `bike_model`, `location`, `avatar_path`, `cover_image_path`. `avatar_url` is **gone — `024`, applied 2026-08-05** after the code repair deployed. `014` had kept it as a fallback rather than dropping it unverified; the verification came back 0 non-NULL on both tables. The name survives in `src/` as a *field on what `lib/data/` returns*, holding the signed URL — never a column. The two `*_path` columns are Storage object paths under `avatars/<uid>/` and `covers/<uid>/`, each pinned to its owner by a CHECK on the row's own `id`. Render them through `resolveAvatarUrls` / `signImagePaths`, never directly. **`username` stores the case the rider typed and is unique case-INSENSITIVELY** (`056`): `Pedro` renders as `Pedro`, while `pedro`, `PEDRO` and `PeDrO` are unavailable to everyone else, because `profiles_username_lower_key` is a unique index on `lower(username)` and `profiles_username_format` is `^[A-Za-z0-9_]{3,25}$` (`056` set the charset, `057` the 25). Read availability through `username_exists(text)` and never through `.eq('username', …)` (case-sensitive) or `.ilike()` (LIKE treats `_` as a wildcard and the charset allows underscores). **`username` is durable: once it holds a value, `authenticated` cannot return it to NULL** (`038`). The rule is **"once set, never unset", not "once onboarded"**, so a rider mid-wizard cannot free a taken name either; a rename is still permitted, unbuilt and unsurfaced rather than decided. **`authenticated` holds no DELETE grant (`042`)** — deleting your own row reaches the same invisibility `038` closed, by a different door, and until `042` it was refused only by the *absence of a DELETE policy*, so any future DELETE policy added for an unrelated reason would have reopened it silently. The row is still reaped by the cascade from `auth.users`, which is how account deletion removes it (`029`–`032`) and which consults no table grant at all. |
| `rides` | Rides with `organizer_id → profiles`, optional `club_id → clubs`. **Its SELECT policy has FOUR audience arms since `083`** — the organizer, a public ride, a ride in a club you belong to, and a live `ride_invites` row — the last three dominated by the block check. That fourth arm is a route into a **private club's** ride that did not exist before: a rider who is not a member of that club, invited to one of its rides, reads that ride and its crew and no part of the club. `private.can_read_ride` is a second implementation of the same predicate and moves in the SAME migration, never afterwards. The organizer FK is `ON DELETE CASCADE`, so **a ride is cancelled by its organizer's account deletion** — deliberate (a ride is one person's plan), and the crew is not notified because there is nothing to notify them with. `club_id` is `ON DELETE SET NULL`, which `029` treats as a trap rather than a default: a private club's ride left with `club_id` NULL and `is_public` false is visible only to its organizer while its `ride_members` rows survive, so the transfer function deletes a club's rides with the club instead. **`max_riders` is GONE — `077` (PD-293) dropped the column and `063`'s join gate together**, so nothing caps a crew any more; `018`'s `rides_max_riders_range` went with the column. `063` was correct about the race it fixed, but the design draws no capacity affordance anywhere, so the cap could only ever surface as an unexplained refusal at the RSVP. **`rides` carries nine CHECKs now.** **Grants are per column as of `045`, widened by `051` and `067` and narrowed by `077`** — `insert` over **13** columns, `update` over **14**, `select` over 17 (`080` added `timezone` to all three); `created_at` is server-owned (neither verb), and `id` and `organizer_id` are insertable but **not** updatable, so a hand-off is refused by the grant as well as by the UPDATE `with check`. **There is no `updated_at` column**, which is a known gap rather than a decision now that `updateRide` ships. Re-derive the lists from `information_schema.column_privileges` scoped to `grantee = 'authenticated'`. **`051` adds five nullable tile columns and `067` a sixth** — `latitude`, `longitude`, `geocode_confidence`, `map_card_path`, `map_detail_path`, and `start_place_id`. NULL is the **normal** state and the designed fallback, not an error: every ride that existed when `051` applied has them NULL and there is no backfill, because the render runs under the organizer's own JWT and nothing is entitled to render a ride it does not organise. A ride gets its tile the next time its organizer edits it. **`059`: a ride created in the `clubs.is_default` club notifies NOBODY.** `rides` INSERT is `club_id is null or private.is_club_member(club_id)`, so after `058` every rider may create a ride in the welcome club, and `036` §7.5's member fan-out would have written one `notifications` row per rider in the app, inside that rider's own INSERT, repeatable at will. The ride itself is unaffected and still visible to every member. **`067` replaces `rides_geocode_coupling` with the three-armed `rides_location_coupling`, and that constraint no longer exists by its old name** — a search for it finds only stale comments. Four CHECKs are coupled to the location columns now (`rides_location_coupling`, `rides_map_paths_need_a_coordinate`, `rides_map_paths_pinned_to_organizer`, `rides_start_place_id_length`), and `rides` carries **nine** in total — `077` dropped `rides_max_riders_range` with its column and `080` added `rides_timezone_is_bounded`. **Nothing measures that number** — the RLS suite pins a CHECK count for `clubs` and `postcards` and not for `rides`, and no `docs:check` claim covers it — so re-derive it rather than trusting either sentence: `select count(*) from pg_constraint where conrelid='public.rides'::regclass and contype='c'`. **The old one-directional rule is only one of three arms**: *"a coordinate needs a confidence at or above the floor"* is now true of the **geocoded** arm alone. A **picked** coordinate carries a `start_place_id` and NO confidence — a rider chose the point, so there is no vendor score to record and one beside it would be a fiction. The third arm is no location at all. A tile path still needs a coordinate, and a coordinate **may** exist without a path — a successful geocode followed by a failed render is a real end state. **The column that distinguishes the two writers is `start_place_id`, not a flag**, which is why there is no enum to keep in step. Two `BEFORE UPDATE` triggers hold the precedence — `clear_ride_map_tiles` drops the group when the text or the pick changes, `protect_picked_ride_location` restores a picked coordinate a geocode tried to move — and **neither raises**, so on UPDATE the CHECK is not what a mixed statement hits: the triggers normalise it first. The CHECK is still reachable on an UPDATE that fires neither, and on every INSERT, where nothing normalises anything. **Since `080` a ride also carries `timezone`, the IANA zone of its meeting point (PD-193), and it is deliberately NOT part of that location group** — a stale zone survives a location change and `resolve-ride-location` overwrites it when the geocode lands. Putting it in the group was written first and measured wrong: `updateRide` resolves `departure_at` against the zone the edit form was rendering in, so a save changing the address AND the time carried an instant expressed in a zone the clearing trigger dropped, and the ride rendered an hour the rider never typed (09:30 typed, 10:30 drawn). `080.5` is that case as an assertion. NULL means "we do not know" and falls back to `APP_TIME_ZONE` on both the read and the write side, which is what every ride did before the column. **The invariant a third `BEFORE` trigger holds is the point of it**: `enforce_ride_timezone` normalises a name absent from `pg_timezone_names` to NULL (never raises — the map pipeline that writes this column fails open at every other stage, and on the picked path the write is the rider's own INSERT), and then, on any UPDATE that moves `timezone` while leaving `departure_at` alone, shifts `departure_at` with `AT TIME ZONE` so the organizer's typed wall-clock is preserved. That guard is what keeps it off an ordinary edit: `updateRide` always sends `departure_at`, so a statement that genuinely moved the ride wins, while `resolve-ride-location` sends the zone alone and therefore shifts. `rides_timezone_is_bounded` (64 characters) is **unreachable through that trigger** and is kept as a floor under `session_replication_role = replica`; the suite asserts both directions. **Grants are additive per `067`'s pattern** — `insert (timezone)` because a PICKED start supplies its zone at ride creation, which is the one moment it is knowable without a geocode, and `update (timezone)` because a TYPED one learns it afterwards. **Trigger NAME order is load-bearing** and Postgres fires `BEFORE` row triggers in it, so `enforce_ride_timezone` reads the row `clear_ride_map_tiles` has already rewritten. `080.7` asserts the whole `BEFORE`-row list rather than the three location ones filtered out of it — `enforce_participation_gate` and `enforce_ride_club_audience` both sort between the first two, and a filtered assertion is blind to a third landing there (and, comparing a name-ordered aggregate against those same names sorted, is a tautology with respect to order). `rides` now carries **six** triggers. Both path columns are pinned to `'ride-maps/' || organizer_id || '/%'`. **The grant is per-column since `045`**, so `051` grants UPDATE on the five explicitly; the proposal's premise that `rides` was table-level went stale a day before the build and would have failed every column write with `42501`. |
| `ride_members` | `(ride_id, user_id)` composite PK. `status`: `going` \| `maybe`. **Nothing caps a crew — `063` capped one at `rides.max_riders` for six days and `077` (PD-293) dropped both the trigger and the column.** The reason is not that `063` was wrong about its mechanism (it was a `security definer` `BEFORE INSERT OR UPDATE` trigger taking a `for no key update` on the parent row, because a check-then-insert races two riders taking the last seat) but that the design draws **no** capacity affordance anywhere, so the rule could only ever reach a rider as an unexplained refusal. **So this table is unbounded in the database**, and the only ceiling left is `RIDE_CREW_LIMIT = 200` on what the crew rail renders. That is fine at this scale and is the thing to reopen if one ride ever attracts thousands. **Grants are per column as of `048`** — `insert` and `update` both over `(ride_id, user_id, status)`; `joined_at` is server-owned (neither verb), because `getRideCrew` orders on it ASC and caps at 200 with no pagination, so a back-dated value bought a place inside the truncation window ahead of genuine crew. All three UPDATE columns are **required, not tidy**: `setRideAttendance` is an upsert and PostgREST's `ON CONFLICT DO UPDATE` SET list carries every payload column *including both conflict columns*, so granting `status` alone fails every repeat RSVP with 42501. Re-derive from `information_schema.column_privileges` scoped to `grantee = 'authenticated'`. |
| `clubs` | Clubs with `owner_id → profiles`. **A club outlives its owner as of `029`.** The FK is `ON DELETE CASCADE` and `postcards.club_id → clubs` cascades behind it, so deleting an owner would destroy every postcard every *other* member ever posted there — `009` reasoned that link out correctly for a club deleted *by* its owner and never considered it arriving as a side effect of a third party's erasure. `private.transfer_owned_clubs` hands the club to its longest-tenured remaining admin, else member, and only deletes it when nobody is left. Reached through `031`'s `service_role`-only wrapper, never by a client. **An owner deletes their OWN club through `public.delete_owned_club(p_club_id uuid)` (`043`), never a bare `.delete()`**: the `rides` DELETE policy is `auth.uid() = organizer_id` with no club-owner arm, so a client delete leaves every private ride in the club detached by `SET NULL`, visible to its organizer alone, with its crew list and chat unreadable — and for a private club that is every ride. The RPC is `security definer`, re-checks `owner_id = auth.uid()` in its own body (RLS does not apply inside it), deletes the club's `is_public = false` rides with the club, and returns the club's own Storage object paths so the caller can delete the bytes. Cascade-deleted postcards' images belong to other riders and are permanently orphaned — `PD-94`. **Grants are per column as of `045`** — `insert` over seven columns, `update` over five; `created_at` is server-owned (neither verb), which matters more here than on `rides` because `getClubsToExplore` **sorts on it**, so while it was writable an owner could float their club to the top of Explore permanently. `id` and `owner_id` are insertable but **not** updatable, so a hand-off is refused by the grant as well as by the UPDATE `with check`. **There is no `updated_at` column** — the same known gap `rides` has. **The club audience predicate is `private.is_club_member(club_id)` and it is NOT a membership-only test as of `054`**: it is true for a rider holding a `club_members` row **or** named by `clubs.owner_id`, so a club's owner reaches their own club exactly as a member does whether or not that row exists. Ten policies across `rides`, `postcards`, `club_members`, `feed_reads` and `clubs` share it — re-derive with `select tablename, policyname, cmd from pg_policies where (coalesce(qual,'')||coalesce(with_check,'')) like '%is_club_member%'` — and a further set inherits it transitively through an RLS-filtered `EXISTS`, **including two `storage.objects` SELECT policies, so the reach extends to postcard image bytes and ride map tiles**. Before `054` the owner arm existed on `clubs` SELECT alone, so an owner holding no membership row saw their club and none of its rides, postcards or roster, and could not create a ride in it either. Two things the arm does **not** do: it never steps past a block (every occurrence is dominated by a `private.is_blocked` conjunct, the only escaping disjuncts being self-identity, which `blocks_no_self_block` makes safe), and it confers no moderation — `rides` writes stay `organizer_id`-keyed, `postcards` UPDATE `author_id`-keyed, `club_members` DELETE `auth.uid() = user_id`. It is also **caller-relative** — it resolves `auth.uid()` — so it must never compute a notification fan-out recipient set (`036` trap (c)). **`060` split the body out into `private.is_club_member_for(candidate, target_club_id)` and made this a wrapper over it**, so the same rule now has a subject-taking reading a fan-out CAN use, with one body behind both and no second copy to drift. That is what lets `ride_created_in_club` union `clubs.owner_id` into its recipients — via `private.can_read_ride(candidate, ride)`, which measures the read rather than asserting it — so an ownerless owner **is** now notified of rides in their own club, where `036` §7.5 withheld it. Neither new function is executable by any client role: both take a subject, so a rider holding EXECUTE would have a block oracle and a private-club membership oracle. **`058` adds `is_default`: the welcome club every rider joins the moment they complete onboarding.** At most one row may carry it (`clubs_one_default_club`, a partial unique index) and it must be public (`clubs_default_club_is_public`). `authenticated` holds **SELECT and neither write verb**, and that asymmetry is the security boundary rather than tidiness: `clubs` UPDATE's policy already lets an owner write their own row, so the column grant is the only thing between a rider and pointing every future signup at a club of theirs. **Which club carries it is data, not schema** — `Welcome club` on PROD, `Welcome club (dev)` on DEV, nothing on the RLS suite's scratch database — so read it (`select id, name from clubs where is_default`) rather than expecting an id in the migration, and expect NONE to be a working state: `complete_onboarding` joins nobody and onboarding is unaffected. **`058` changes neither grant count above** — `insert` is still over seven columns and `update` still over five, because `is_default` gets neither. **`059` makes the default club undeletable through `delete_owned_club`** (42501, the same refusal shape), because `029`'s succession can hand that club to an ordinary rider — it always has members now, so it never reaches the "nobody left, delete it" arm — and one tap would switch auto-join off for every future rider. Unflag it and it deletes normally. The inherited rename and imagery rights are a KNOWN GAP, reachable only by the welcome club's owner deleting their own account — **and `095` (PD-194) narrows it to exactly that**, because a voluntary leave of the `is_default` club is now refused too, so the welcome club is unleavable and undeletable by any rider by any route. **`095` also gives an owner a way OUT of an ordinary club that is not destructive.** Product owner, 2026-08-31: *"an owner can only leave a club if there is at least one more admin associated with it, or if it has no members."* Three arms, and the database decides which applies from the true state rather than from a roster count a client holds: **(1)** another rider at `role = 'admin'` — `public.leave_owned_club(p_club_id uuid) returns table (object_path text)` transfers the club to the longest-standing such admin (`joined_at` ascending, tie-broken by `user_id`, chosen by `private.pick_club_admin_successor`), sets their roster row to `owner`, and **DELETES** the leaver's row rather than demoting it — the one place this diverges from `032`, which demotes because its transfer commits mid-account-deletion and must survive a failure after it; **(2)** no other member — `leave_owned_club` REFUSES and the client opens the existing `DeleteClubSheet`, so `043`'s `delete_owned_club` stays the only deletion route and no call a rider makes as "leave" can destroy a club; **(3)** members but no other admin — refused, with the remedy named. **Arms 2 and 3 share ONE raise site with ONE message**, and splitting it is forbidden: an owner blocked with their club's only member would otherwise learn that a member they cannot see exists, which is one bit about a person a block is hiding. **The RPC takes a club and no rider id**, so a successor cannot be proposed and `owner` stays nameable by no client, the corollary of `019`'s rule about `admin`. Four barriers make it an RPC rather than a policy change and the first is missed by anyone starting at the policy: `045` grants `authenticated` no UPDATE on `owner_id` at all, so a client transfer fails `42501` before any policy runs; `clubs` UPDATE carries `using` **and** `with check` on `auth.uid() = owner_id`; `club_members` has no UPDATE policy; and PostgREST has no transaction, so a three-write transfer done as three round trips tears. A fifth fires on the HAPPY path: **`016`'s two path CHECKs pin both images to the row's current `owner_id`, so any `update clubs set owner_id` raises `23514` while either is non-null** — the transfer clears both in the SAME statement (row CHECKs are evaluated at statement end) and returns the surrendered paths, the leaver being the only rider whose Storage policy reaches those bytes. **Blocking does not filter the successor and cannot trap an owner**: the candidate query runs inside a definer function, so a block between the leaver and a candidate admin is invisible to it — otherwise an admin could make themselves invisible by clicking Block, drop the club to arm 3, and leave their owner with no exit but destroying a club full of other people's postcards. The confirmation therefore must **never name the successor**, since naming needs a per-viewer read that returns nothing for a blocked admin and a privileged one is a block-visibility leak. The successor is told **nothing** — no notification, deferred with a reason rather than skipped. **Since `066` a club carries its OWN location** — `location_name`, `location_place_id`, `latitude`, `longitude` (PD-259), filled from a picked place and **never from the creator's profile**: product owner, *"the club location is not the location of the rider who created it."* All four move together or none does (`clubs_location_coupling`), and NULL is the normal state. **`location_place_id` is provenance and never a join key** — it holds a third party's opaque id, namespaced by provider (`geoapify:...` since `070`), so it can dangle and nothing will say so. There is no foreign key behind it and there never was: `066` wrote it against `public.places`, which was reloaded wholesale so a FK would have blocked every reload or wiped every club's location on one — and `070` dropped that table entirely, which is why the column's independence is now the only thing holding the design up rather than a convenience. `069` widened the bound from 100 to 512 characters for the same reason. The grants are ADDITIVE on top of `045`'s allowlist, so `created_at` and `is_default` stay unwritable. No new policy: the columns live on `clubs`, so `001`'s SELECT policy is the whole answer and a private club's location is visible to its members alone. **`085` (PD-325) makes a PRIVATE club's name, avatar path, location, coordinates and member count reachable by any signed-in rider — and it does NOT touch this table's SELECT policy or `private.can_read_club`, both of which the suite pins by equality at `085.1`/`085.2`.** The reach lives in ONE function, `public.discoverable_private_clubs(target_club, page_size)`, which returns those seven columns and nothing else: no description, no cover, no `owner_id`, no `created_at`, no rides, postcards, threads or roster. That shape is the disclosure and `085.4` pins the return list against `pg_get_function_result`, so an eighth column is a red test rather than a code review. **The accessor route was chosen over a policy arm because an arm here moves two surfaces nobody would list**: `016`'s two `storage.objects` policies delegate to this policy, so the club's own cover photograph would become readable to a non-member; and `036` §3's `notifications` SELECT conjunct would start resolving for any `club_id`-carrying row a non-member happens to hold. It is also structurally insufficient on its own — an arm predicated on a request row is circular, since making a request needs a club id and only a list supplies one. The avatar path is returned and **SIGNS since `089`** (PD-335), on the product owner's decision of 2026-08-28: `016`'s avatar policy carries a third disjunct through `private.club_avatar_is_discoverable`, a definer helper, because the inline `exists` the design pre-wrote reads `clubs` under the reader's own RLS and so could never have worked. **The COVER is not included and is pinned byte-for-byte** — an avatar is the club's identity, a cover is its content. `085.6` pinned the opposite and could observe neither answer: its fixture named `bucket_id = 'club-avatars'` where every `016` policy opens with `bucket_id = 'media'`, so both of its assertions read zero for a reason with nothing to do with the club. `089.8` replaces it with a fixture that exists. **`085` (PD-326) adds three RPCs that write `club_members` and no policy**: `remove_club_member`, `promote_club_member` and `demote_club_admin`, each taking a CLUB and a RIDER and **no role argument at all**, so `019`'s property that `admin` is claimable by no client survives the first write path that ever sets it. An admin may act on members; only the OWNER may act on admins, and nobody removes or demotes the owner. `088.1` pins that `club_members` still has SELECT, INSERT and DELETE policies and nothing else — `036` §7.6 relies on the missing UPDATE policy, and RLS cannot scope an UPDATE to one column. |
| `club_members` | `(club_id, user_id)` composite PK. `role`: `owner` \| `admin` \| `member`. **Grants are per column as of `048`** — `insert` and `update` both over `(club_id, user_id, role)`; `joined_at` is server-owned (neither verb), because the roster sorts on it ASC and caps at 200 with no pagination. **The UPDATE grant is dead today** — there is no UPDATE policy on this table at all, which is what `036` §7.6 relies on for "nobody can promote an admin" — and it is narrowed anyway so a future member-promotion policy cannot inherit `joined_at` for free. Re-derive from `information_schema.column_privileges` scoped to `grantee = 'authenticated'`. **Since `058` this table has a writer no rider triggers**: `complete_onboarding()` inserts a `member` row here for the `clubs.is_default` club on the transition into completion. It runs as the function owner, so neither the INSERT policy nor `enforce_participation_gate` applies — and it is wrapped in a `when others` block, because a raise there would roll back the completion stamp in the same transaction and strand the rider in a wizard decision #5 gives no way out of. `private.notify_club_joined()` returns early for that club, or its owner would receive one notification per signup for ever. The rider can still leave: the DELETE policy is unchanged. **The roster is no longer opt-in**, so the 200-row cap above now describes a screen that can only ever show the 200 earliest members of a club containing every rider — and `members_count` on that club's card is the app's onboarded-rider count, visible to every signed-in rider. **`085` (PD-325) adds a THIRD writer, `private.join_club_from_request(rider, target_club)`**, reached only from `public.approve_club_join_request`. It exists because this table's INSERT policy admits only a public or self-owned club, so an admin approving a request into a PRIVATE one simply cannot insert the row from the client — and the policy is deliberately UNCHANGED (pinned at `085.3`), the definer writer being the whole mechanism. Like `complete_onboarding` it runs as the function owner, so neither the INSERT policy nor `enforce_participation_gate` applies; unlike it, it restates BOTH in its own body — the participation gate through the new subject-taking `private.may_participate_for(candidate)`, because the CALLER is the admin and the SUBJECT is the requester and the caller-relative form would answer for the wrong rider, and the owner block because a request that predates one must not be approvable. It writes `'member'` as a literal and takes no role argument, which is what keeps `019`'s rule that `admin` is claimable by no client true through the new path. **No compensating gate trigger was added here and none should be** (`078.9`): one could never fire, because `current_user` inside a definer body is the owner, and it would make coverage read complete while gating nothing. **`093` (PD-360) adds a FOURTH writer, `private.join_club_from_invite(rider, target_club, admitter, link)`**, reached from `public.accept_club_invite` and `public.claim_club_invite_link` and from nowhere else. It is `join_club_from_request`'s shape with one more argument: it restates the participation gate through `private.may_participate_for` — never the caller-relative form, `085`'s trap — restates the ADMITTER's authority through `private.may_invite_to_club_for` (re-derived at the moment of the write, so a demoted or departed inviter admits nobody) and restates both blocks, writes `'member'` as a literal with no role argument, and then deletes any pending `club_join_requests` row for the pair **after** the membership so `085`/`087`'s retraction clears the admins' notification. **`093` also adds the column `invite_link_id`** — nullable, `references club_invite_links(id) **on delete set null**`, never cascade, because deleting a link must not delete the riders it admitted. It is **PROVENANCE ONLY**: no policy, trigger or read predicate may branch on it, and the suite asserts that none does, so a rider admitted by a token is indistinguishable from an accepted invitee, an approved requester and a rider who simply joined a public club everywhere access is decided. It carries **no grant in either direction** — `048`'s per-column INSERT and UPDATE grants over `(club_id, role, user_id)` make a new column unwritable by inheritance rather than by a statement in `093` — and its one purpose is deriving a link's use count, which is read under the admin's own block-dominated RLS and can therefore go **down**. **Still no compensating gate trigger here and there must not be one** (`078.9`). **`095` (PD-194, closing PD-103's club-side half) hangs the table's FIRST DELETE TRIGGER on it**: `private.protect_club_owner_membership`, `before delete … for each row when (current_user = 'authenticated')`, refusing `check_violation` (`23514`, never `42501`, so an assertion cannot pass on the wrong rule firing) when `old.user_id` equals the club's `owner_id`. An owner-membership row now has exactly **two** legal ways to disappear — `public.leave_owned_club`'s transfer, and the club going away — and every other route is refused by the database rather than by a ternary in `ClubOptionsMenu`. **It keys on `clubs.owner_id` and NEVER on `club_members.role`**: the two are permitted to disagree (`054`, PD-128, and `088`'s explicit ownerless-owner arm), so a role-keyed guard would let an ownerless owner delete a row the invariant needs and would refuse a delete on a stale `owner` row for a club somebody else owns. Keyed to `profiles` alone the rows would outlive the timeline entry they decorate, be unreachable from every screen, and **REAPPEAR on a rejoin**, showing a rider as welcomed in September by riders who did nothing in September; `add-club-timeline` requires a rejoin be indistinguishable from a first join, and this key is what delivers it. `092.10` is the assertion, and it goes red against a bare key. `role` is not in that primary key, so `088`'s `promote_club_member` / `demote_club_admin` disturb no wave. **`user_id` — the WAVER — keeps its own `→ profiles ON DELETE CASCADE`**, so there are **two** foreign keys into `profiles` across the two wave tables and not three; the subject's erasure arrives one hop away, through `club_members`. Both lead an index of their own (`club_thread_waves_user_idx`, `club_join_waves_user_idx`), because both primary keys lead with another column and `029`'s standing rule would otherwise make every account deletion a sequential scan. **Audience is INHERITED**: SELECT is `user_id = auth.uid() or (exists (select 1 from club_members m where m.club_id = club_join_waves.club_id and m.user_id = club_join_waves.subject_user_id) and not private.is_blocked(auth.uid(), user_id))`, the own-row branch hoisted for the reason given on `club_thread_waves`. **BOTH qualifications are load-bearing** — `club_members` has a column of each name, so an unqualified comparison deparses to `m.club_id = m.club_id` and the EXISTS degenerates into "can I read any roster row anywhere"; `092.2` and `092.5` each catch one half behaviourally and `092.7` pins both structurally. **The inherited audience is ASYMMETRIC with `club_thread_waves` and that is not an oversight**: `club_members` SELECT carries a public-club disjunct and `club_threads` SELECT does not, so a non-member of a PUBLIC club reads — and, the INSERT policy being the same `EXISTS`, **writes** — join waves in it while reading no thread wave at all. The capability spec's role table said such a rider may not wave a join; that cell was corrected to match the policy, because refusing the write would mean restating membership, which the same capability forbids by name. `092.1` asserts both halves. INSERT additionally requires **`user_id <> subject_user_id`** — a self-welcome expresses nothing — which keeps a self-addressed row out of the fan-out's path rather than relying on the fan-out to exclude it; the fan-out excludes it too and neither is redundant. DELETE is `using (user_id = auth.uid())`, reachable for the same hoisted-SELECT reason described on `club_thread_waves`. `revoke all` then `grant select, delete` at table level and `grant insert (club_id, subject_user_id, user_id)` per column, `created_at` on neither list. No UPDATE policy, no UPDATE grant. Carries the participation gate (the nineteenth). **TWO fan-out triggers, and they are the only ones in `092`**: `private.notify_club_waved` writes exactly ONE `notifications` row addressed to `subject_user_id` — not the owner, not the admins, not the other members — and `private.retract_club_waved` removes it on delete, scoped by **all four** of `user_id`, `type`, `actor_id` and `club_id` (`036` §7.2: a subset scope is a write one rider can aim at another's row). The retraction also fires on CASCADED deletes, which here is useful rather than merely harmless — leaving the club takes the waves and their welcome notifications together. No `pg_trigger_depth` guard. **Every `club_members` row predating `092` is wavable the moment it applies and NOTHING is backfilled.** RETENTION: indefinite, dying with the MEMBERSHIP, the subject's account or the reactor's — three cascades, no scheduled job. |
| `club_invites` | One row per (club, invited rider), added by `093` (PD-360). **THE MIRROR IMAGE OF `club_join_requests` ACROSS THE DIRECTION OF THE ASK, and two tables rather than one because it is the POLICIES that mirror** — an authorised member INSERTs, the INVITEE answers, a refusal is terminal against the INVITER, and the club's admins may clear one. Merging the two would put a `case direction` inside every policy qual, inside the status CHECK and inside both RPCs. **`unique (club_id, invitee_id)` and `status` has TWO values, `pending` and `declined`** — `085`'s rule and not `083`'s: for a RIDE the invite row IS the audience arm, so `083` keeps `accepted`; for a CLUB the MEMBERSHIP is the audience, so **accepting DELETES this row** and a surviving `accepted` row beside that unique key would make a club a rider once left un-invitable for ever. **WHO MAY INVITE IS DECIDED BY THE CLUB'S VISIBILITY AT THE MOMENT OF USE AND NEVER BY A COLUMN HERE**: `private.may_invite_to_club_for` is an ADMIN on a private club (`085`'s approval set exactly, so a declined rider cannot be let in by somebody with no authority to reverse the decline) and ANY MEMBER on a public one (where the row is a POINTER rather than a grant, the recipient being able to open and join the club already). **That predicate is RE-DERIVED at every accept and every claim** — the first grant in this schema whose validity is checked at use rather than fixed at creation — so an invite from a since-demoted or since-departed rider stops working, and a member's pointer into a public club does not silently become a grant into a private one after a flip. **AUDIENCE: the invitee, the inviter and the club's ADMINS**, all dominated by a block conjunct on BOTH parties, and **no arm reads `clubs`** — one that did would hand every member of a public club the invites of a private one, and for a private club it would be circular. The admin disjunct is **not** that arm and is not decoration: RLS filters a DELETE by what the caller may READ, so without it the DELETE policy's admin arm is a silent `DELETE 0` and the decided *"an admin may clear a co-admin's declined invite"* cannot happen. An ordinary member reads none. **A PENDING INVITE GRANTS NOTHING AT ALL** — the invitee reads no roster, thread, message, ride or postcard of the club, and the only policy that moves for them is `notifications`. INSERT is granted **per column** over `(id, club_id, invitee_id, inviter_id)` — `status`, `created_at` and `responded_at` on none of them — and there is **no UPDATE policy and no UPDATE grant at all**, so `public.accept_club_invite` and `public.decline_club_invite` are the only writers of `status`. A BEFORE INSERT trigger, `private.enforce_club_invite_is_admissible`, refuses an invite to the owner, to an existing member, to the default club or to a rider with a **pending join request** — the two mechanisms meeting, resolved in favour of the request the rider started. **Its first statement is load-bearing rather than a fast path**: a BEFORE ROW trigger fires BEFORE the RLS `WITH CHECK` (measured, Postgres 17), so without a short-circuit for a caller with no authority the trigger is a MEMBERSHIP ORACLE for every private club, readable by comparing `23514` against `42501`. It deliberately tests **no block**, a raise naming one being a marker decision #2 forbids; blocks are enforced at four places that disclose nothing — the INSERT policy, the fan-out, the accessor and the accept. **RETENTION: indefinite and there is NO EXPIRY**, an expiring invite being a silent withdrawal neither party is told about; three `on delete cascade` FKs (club, invitee, inviter) are the whole window, and account deletion reaches it from BOTH rider ends. There is deliberately no `responded_by` and no `updated_at`. The twentieth `enforce_participation_gate` trigger is on this table. |
| `club_invite_links` | One row per shareable invite token into a **private** club, added by `093` (PD-360). **The second place in this schema where possession of a SECRET rather than an identity buys reach** — `token` is 32 lowercase hex from `extensions.gen_random_bytes(16)`, 128 bits, and the grant is what guarantees it: `authenticated` may INSERT only `(id, club_id, created_by)`, so no client can name `token`, `expires_at`, `created_at` or `revoked_at`, and there is **no UPDATE policy and no UPDATE grant at all**, making `public.revoke_club_invite_link` the only writer of `revoked_at`. A CHECK pins the token's shape. **`expires_at` is a plain column DEFAULT of `now() + interval '14 days'`, not `091`'s BEFORE INSERT trigger** — `091` needed one because `least(rides.departure_at, …)` reads another table, and a club has no departure and therefore no natural death, which makes this ceiling the whole time-based control rather than a cap on a shorter one. **A PUBLIC CLUB GETS NO TOKEN AND THAT IS A DECISION**: `clubs` SELECT admits every signed-in rider and `club_members` INSERT lets any of them join, so the plain URL already carries the entire grant a token could carry and a token there would be a capability surface with no capability behind it. `private.may_mint_club_link_for` is where that lives. **SELECT, INSERT and DELETE are all `private.is_club_admin`-based, so a link FOLLOWS THE CLUB rather than its minter** and a co-admin who did not mint may list and revoke it; **no claimer ever reads the row**, which is what makes every token a genuine bearer credential rather than a lookup key. **ONE predicate decides reach for both public RPCs**: `private.club_invite_link_reachable_by(token, uid, lock)` — live, **plus the minter STILL AUTHORISED** (`may_invite_to_club_for`, re-derived, so a demotion or a departure kills every link that rider minted), plus `private.is_blocked` in both directions with the minter AND with the club's owner, plus both participation stamps, plus not already a member and not the owner. Neither `club_invite_link_preview` nor `claim_club_invite_link` may test a block or a stamp in its own body, which the suite asserts by reading `prosrc`: there is **no policy underneath either**, so a definer preview that forgot the block check would be a bypass reachable by URL with nothing in `pg_policy` to reveal it. It deliberately asks `may_invite_to_club_for` and **not** `may_mint_club_link_for`, so a club that has since become PUBLIC stays claimable — the claim then admits nothing the plain URL would not. **Neither RPC is `stable`, and the label is not cosmetic**: `for share` is illegal in a non-volatile function, and PostgREST serves a `stable` function over GET, which would put a live capability token in a query string and therefore in the project's own request log. The preview returns **exactly six named columns** (club id, name, `avatar_path`, `location_name`, `members_count`, `is_public`) and **never a roster, never `clubs.*`, never the description, cover, owner, age or COORDINATES** — the landing screen draws none of those, and `is_public` is here precisely because a token can outlive a flip. It returns **zero rows** for every dead state and raises nothing; the claim has exactly **one** raise site, so expired, revoked, club deleted, minter demoted or departed, blocked either way, un-onboarded, already a member, the owner, malformed and guessed are one indistinguishable answer. **A CLAIM ADMITS DIRECTLY, with no admin approval** (product owner, 2026-08-31, with the refinement that the rider browses the club first and the token is spent by a TAP and never by a render — a claim on session establishment would admit whoever signs in next on a shared tab, which is a perfectly valid claim at this layer and therefore invisible to every assertion in `supabase/tests/`). **Revoke ejects nobody**; unlike a ride, `088`'s `remove_club_member` *can* eject — but **removal does NOT bar re-entry through a live token**, because nothing records it, and closing that gap is **PD-361**. The claim takes `for share` on the link row for `091`'s reason. **RETENTION: the row is kept after the token dies**, because `club_members.invite_link_id` points at it; two `on delete cascade` FKs (club, minter) are the whole window. The twenty-first `enforce_participation_gate` trigger is on this table. |
