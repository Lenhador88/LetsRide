# Schema — the per-table contract

Every row here is a *rule*, not a description: the grant lists, the cascade behaviour and the
audience predicates are what the RLS suite asserts. Re-derive a grant list from
`information_schema.column_privileges` scoped to `grantee = 'authenticated'` rather than reading
it here.

**Schema (key tables):**

| Table | Purpose |
|---|---|
| `profiles` | One per auth user. PK = auth user UUID. Has `username`, `bio`, `bike_model`, `location`, `avatar_path`, `cover_image_path`. `avatar_url` is **gone — `024`, applied 2026-08-05** after the code repair deployed. `014` had kept it as a fallback rather than dropping it unverified; the verification came back 0 non-NULL on both tables. The name survives in `src/` as a *field on what `lib/data/` returns*, holding the signed URL — never a column. The two `*_path` columns are Storage object paths under `avatars/<uid>/` and `covers/<uid>/`, each pinned to its owner by a CHECK on the row's own `id`. Render them through `resolveAvatarUrls` / `signImagePaths`, never directly. **`username` stores the case the rider typed and is unique case-INSENSITIVELY** (`056`): `Pedro` renders as `Pedro`, while `pedro`, `PEDRO` and `PeDrO` are unavailable to everyone else, because `profiles_username_lower_key` is a unique index on `lower(username)` and `profiles_username_format` is `^[A-Za-z0-9_]{3,25}$` (`056` set the charset, `057` the 25). Read availability through `username_exists(text)` and never through `.eq('username', …)` (case-sensitive) or `.ilike()` (LIKE treats `_` as a wildcard and the charset allows underscores). **`username` is durable: once it holds a value, `authenticated` cannot return it to NULL** (`038`). The rule is **"once set, never unset", not "once onboarded"**, so a rider mid-wizard cannot free a taken name either; a rename is still permitted, unbuilt and unsurfaced rather than decided. **`authenticated` holds no DELETE grant (`042`)** — deleting your own row reaches the same invisibility `038` closed, by a different door, and until `042` it was refused only by the *absence of a DELETE policy*, so any future DELETE policy added for an unrelated reason would have reopened it silently. The row is still reaped by the cascade from `auth.users`, which is how account deletion removes it (`029`–`032`) and which consults no table grant at all. |
| `rides` | Rides with `organizer_id → profiles`, optional `club_id → clubs`. The organizer FK is `ON DELETE CASCADE`, so **a ride is cancelled by its organizer's account deletion** — deliberate (a ride is one person's plan), and the crew is not notified because there is nothing to notify them with. `club_id` is `ON DELETE SET NULL`, which `029` treats as a trap rather than a default: a private club's ride left with `club_id` NULL and `is_public` false is visible only to its organizer while its `ride_members` rows survive, so the transfer function deletes a club's rides with the club instead. **`max_riders` is GONE — `077` (PD-293) dropped the column and `063`'s join gate together**, so nothing caps a crew any more; `018`'s `rides_max_riders_range` went with the column. `063` was correct about the race it fixed, but the design draws no capacity affordance anywhere, so the cap could only ever surface as an unexplained refusal at the RSVP. **`rides` carries eight CHECKs now, not nine.** **Grants are per column as of `045`, widened by `051` and `067` and narrowed by `077`** — `insert` over **12** columns, `update` over **13**, `select` over 16; `created_at` is server-owned (neither verb), and `id` and `organizer_id` are insertable but **not** updatable, so a hand-off is refused by the grant as well as by the UPDATE `with check`. **There is no `updated_at` column**, which is a known gap rather than a decision now that `updateRide` ships. Re-derive the lists from `information_schema.column_privileges` scoped to `grantee = 'authenticated'`. **`051` adds five nullable tile columns and `067` a sixth** — `latitude`, `longitude`, `geocode_confidence`, `map_card_path`, `map_detail_path`, and `start_place_id`. NULL is the **normal** state and the designed fallback, not an error: every ride that existed when `051` applied has them NULL and there is no backfill, because the render runs under the organizer's own JWT and nothing is entitled to render a ride it does not organise. A ride gets its tile the next time its organizer edits it. **`059`: a ride created in the `clubs.is_default` club notifies NOBODY.** `rides` INSERT is `club_id is null or private.is_club_member(club_id)`, so after `058` every rider may create a ride in the welcome club, and `036` §7.5's member fan-out would have written one `notifications` row per rider in the app, inside that rider's own INSERT, repeatable at will. The ride itself is unaffected and still visible to every member. **`067` replaces `rides_geocode_coupling` with the three-armed `rides_location_coupling`, and that constraint no longer exists by its old name** — a search for it finds only stale comments. Four CHECKs are coupled to the location columns now (`rides_location_coupling`, `rides_map_paths_need_a_coordinate`, `rides_map_paths_pinned_to_organizer`, `rides_start_place_id_length`), and `rides` carries **eight** in total since `077` dropped `rides_max_riders_range` with its column. **Nothing measures that number** — the RLS suite pins a CHECK count for `clubs` and `postcards` and not for `rides`, and no `docs:check` claim covers it — so re-derive it rather than trusting either sentence: `select count(*) from pg_constraint where conrelid='public.rides'::regclass and contype='c'`. **The old one-directional rule is only one of three arms**: *"a coordinate needs a confidence at or above the floor"* is now true of the **geocoded** arm alone. A **picked** coordinate carries a `start_place_id` and NO confidence — a rider chose the point, so there is no vendor score to record and one beside it would be a fiction. The third arm is no location at all. A tile path still needs a coordinate, and a coordinate **may** exist without a path — a successful geocode followed by a failed render is a real end state. **The column that distinguishes the two writers is `start_place_id`, not a flag**, which is why there is no enum to keep in step. Two `BEFORE UPDATE` triggers hold the precedence — `clear_ride_map_tiles` drops the group when the text or the pick changes, `protect_picked_ride_location` restores a picked coordinate a geocode tried to move — and **neither raises**, so on UPDATE the CHECK is not what a mixed statement hits: the triggers normalise it first. The CHECK is still reachable on an UPDATE that fires neither, and on every INSERT, where nothing normalises anything. `rides` now carries **five** triggers. Both path columns are pinned to `'ride-maps/' || organizer_id || '/%'`. **The grant is per-column since `045`**, so `051` grants UPDATE on the five explicitly; the proposal's premise that `rides` was table-level went stale a day before the build and would have failed every column write with `42501`. |
| `ride_members` | `(ride_id, user_id)` composite PK. `status`: `going` \| `maybe`. **Nothing caps a crew — `063` capped one at `rides.max_riders` for six days and `077` (PD-293) dropped both the trigger and the column.** The reason is not that `063` was wrong about its mechanism (it was a `security definer` `BEFORE INSERT OR UPDATE` trigger taking a `for no key update` on the parent row, because a check-then-insert races two riders taking the last seat) but that the design draws **no** capacity affordance anywhere, so the rule could only ever reach a rider as an unexplained refusal. **So this table is unbounded in the database**, and the only ceiling left is `RIDE_CREW_LIMIT = 200` on what the crew rail renders. That is fine at this scale and is the thing to reopen if one ride ever attracts thousands. **Grants are per column as of `048`** — `insert` and `update` both over `(ride_id, user_id, status)`; `joined_at` is server-owned (neither verb), because `getRideCrew` orders on it ASC and caps at 200 with no pagination, so a back-dated value bought a place inside the truncation window ahead of genuine crew. All three UPDATE columns are **required, not tidy**: `setRideAttendance` is an upsert and PostgREST's `ON CONFLICT DO UPDATE` SET list carries every payload column *including both conflict columns*, so granting `status` alone fails every repeat RSVP with 42501. Re-derive from `information_schema.column_privileges` scoped to `grantee = 'authenticated'`. |
| `clubs` | Clubs with `owner_id → profiles`. **A club outlives its owner as of `029`.** The FK is `ON DELETE CASCADE` and `postcards.club_id → clubs` cascades behind it, so deleting an owner would destroy every postcard every *other* member ever posted there — `009` reasoned that link out correctly for a club deleted *by* its owner and never considered it arriving as a side effect of a third party's erasure. `private.transfer_owned_clubs` hands the club to its longest-tenured remaining admin, else member, and only deletes it when nobody is left. Reached through `031`'s `service_role`-only wrapper, never by a client. **An owner deletes their OWN club through `public.delete_owned_club(p_club_id uuid)` (`043`), never a bare `.delete()`**: the `rides` DELETE policy is `auth.uid() = organizer_id` with no club-owner arm, so a client delete leaves every private ride in the club detached by `SET NULL`, visible to its organizer alone, with its crew list and chat unreadable — and for a private club that is every ride. The RPC is `security definer`, re-checks `owner_id = auth.uid()` in its own body (RLS does not apply inside it), deletes the club's `is_public = false` rides with the club, and returns the club's own Storage object paths so the caller can delete the bytes. Cascade-deleted postcards' images belong to other riders and are permanently orphaned — `PD-94`. **Grants are per column as of `045`** — `insert` over seven columns, `update` over five; `created_at` is server-owned (neither verb), which matters more here than on `rides` because `getClubsToExplore` **sorts on it**, so while it was writable an owner could float their club to the top of Explore permanently. `id` and `owner_id` are insertable but **not** updatable, so a hand-off is refused by the grant as well as by the UPDATE `with check`. **There is no `updated_at` column** — the same known gap `rides` has. **The club audience predicate is `private.is_club_member(club_id)` and it is NOT a membership-only test as of `054`**: it is true for a rider holding a `club_members` row **or** named by `clubs.owner_id`, so a club's owner reaches their own club exactly as a member does whether or not that row exists. Ten policies across `rides`, `postcards`, `club_members`, `feed_reads` and `clubs` share it — re-derive with `select tablename, policyname, cmd from pg_policies where (coalesce(qual,'')||coalesce(with_check,'')) like '%is_club_member%'` — and a further set inherits it transitively through an RLS-filtered `EXISTS`, **including two `storage.objects` SELECT policies, so the reach extends to postcard image bytes and ride map tiles**. Before `054` the owner arm existed on `clubs` SELECT alone, so an owner holding no membership row saw their club and none of its rides, postcards or roster, and could not create a ride in it either. Two things the arm does **not** do: it never steps past a block (every occurrence is dominated by a `private.is_blocked` conjunct, the only escaping disjuncts being self-identity, which `blocks_no_self_block` makes safe), and it confers no moderation — `rides` writes stay `organizer_id`-keyed, `postcards` UPDATE `author_id`-keyed, `club_members` DELETE `auth.uid() = user_id`. It is also **caller-relative** — it resolves `auth.uid()` — so it must never compute a notification fan-out recipient set (`036` trap (c)). **`060` split the body out into `private.is_club_member_for(candidate, target_club_id)` and made this a wrapper over it**, so the same rule now has a subject-taking reading a fan-out CAN use, with one body behind both and no second copy to drift. That is what lets `ride_created_in_club` union `clubs.owner_id` into its recipients — via `private.can_read_ride(candidate, ride)`, which measures the read rather than asserting it — so an ownerless owner **is** now notified of rides in their own club, where `036` §7.5 withheld it. Neither new function is executable by any client role: both take a subject, so a rider holding EXECUTE would have a block oracle and a private-club membership oracle. **`058` adds `is_default`: the welcome club every rider joins the moment they complete onboarding.** At most one row may carry it (`clubs_one_default_club`, a partial unique index) and it must be public (`clubs_default_club_is_public`). `authenticated` holds **SELECT and neither write verb**, and that asymmetry is the security boundary rather than tidiness: `clubs` UPDATE's policy already lets an owner write their own row, so the column grant is the only thing between a rider and pointing every future signup at a club of theirs. **Which club carries it is data, not schema** — `Welcome club` on PROD, `Welcome club (dev)` on DEV, nothing on the RLS suite's scratch database — so read it (`select id, name from clubs where is_default`) rather than expecting an id in the migration, and expect NONE to be a working state: `complete_onboarding` joins nobody and onboarding is unaffected. **`058` changes neither grant count above** — `insert` is still over seven columns and `update` still over five, because `is_default` gets neither. **`059` makes the default club undeletable through `delete_owned_club`** (42501, the same refusal shape), because `029`'s succession can hand that club to an ordinary rider — it always has members now, so it never reaches the "nobody left, delete it" arm — and one tap would switch auto-join off for every future rider. Unflag it and it deletes normally. The inherited rename and imagery rights are a KNOWN GAP, reachable only by the welcome club's owner deleting their own account. **Since `066` a club carries its OWN location** — `location_name`, `location_place_id`, `latitude`, `longitude` (PD-259), filled from a picked place and **never from the creator's profile**: product owner, *"the club location is not the location of the rider who created it."* All four move together or none does (`clubs_location_coupling`), and NULL is the normal state. **`location_place_id` is provenance and never a join key** — it holds a third party's opaque id, namespaced by provider (`geoapify:...` since `070`), so it can dangle and nothing will say so. There is no foreign key behind it and there never was: `066` wrote it against `public.places`, which was reloaded wholesale so a FK would have blocked every reload or wiped every club's location on one — and `070` dropped that table entirely, which is why the column's independence is now the only thing holding the design up rather than a convenience. `069` widened the bound from 100 to 512 characters for the same reason. The grants are ADDITIVE on top of `045`'s allowlist, so `created_at` and `is_default` stay unwritable. No new policy: the columns live on `clubs`, so `001`'s SELECT policy is the whole answer and a private club's location is visible to its members alone. |
| `club_members` | `(club_id, user_id)` composite PK. `role`: `owner` \| `admin` \| `member`. **Grants are per column as of `048`** — `insert` and `update` both over `(club_id, user_id, role)`; `joined_at` is server-owned (neither verb), because the roster sorts on it ASC and caps at 200 with no pagination. **The UPDATE grant is dead today** — there is no UPDATE policy on this table at all, which is what `036` §7.6 relies on for "nobody can promote an admin" — and it is narrowed anyway so a future member-promotion policy cannot inherit `joined_at` for free. Re-derive from `information_schema.column_privileges` scoped to `grantee = 'authenticated'`. **Since `058` this table has a writer no rider triggers**: `complete_onboarding()` inserts a `member` row here for the `clubs.is_default` club on the transition into completion. It runs as the function owner, so neither the INSERT policy nor `enforce_participation_gate` applies — and it is wrapped in a `when others` block, because a raise there would roll back the completion stamp in the same transaction and strand the rider in a wizard decision #5 gives no way out of. `private.notify_club_joined()` returns early for that club, or its owner would receive one notification per signup for ever. The rider can still leave: the DELETE policy is unchanged. **The roster is no longer opt-in**, so the 200-row cap above now describes a screen that can only ever show the 200 earliest members of a club containing every rider — and `members_count` on that club's card is the app's onboarded-rider count, visible to every signed-in rider. |
| ~~`friendships`~~ | **Dropped by `013`, applied 2026-08-04.** Gone from the schema and from `src/`. A v1 leftover; the design has no friendship concept. Listed here only so its absence is not mistaken for an oversight. |
| `postcards` | The photo feed / home screen. `author_id → profiles`, optional `club_id → clubs`, optional `ride_id → rides` (`041`). **`club_id` IS the audience** — NULL means the app-wide feed, set means that club's members. There is deliberately no `is_public` flag. **`ride_id` is a TAG, not a second audience** — the SELECT policy does not mention it, so nulling it changes who can see the postcard by exactly nothing, which is the property that keeps it a tag. Tagging needs the ride visible to the caller **and** `private.is_ride_crew`; neither alone, because a FK is validated with RLS bypassed and a `ride_members` row outlives blocking the organizer. `authenticated` holds no UPDATE grant on it, so a tag is set once at insert — that, not a policy, is what refuses a retag. **And as of `062` it holds no SELECT grant on it either**: the raw uuid is comparable, so a viewer who can resolve neither the ride nor its crew could still group postcards by it, and a select list could not close that because the browser queries PostgREST directly. The Journal filters through `public.ride_journal_postcard_ids(ride uuid)` instead — `security definer`, in `public` so PostgREST can route to it, returning **ids only** so the rows still come back through the ordinary RLS-governed read. Postgres checks a column privilege to FILTER as well as to return, which is why the grant and the Journal wanted the identical privilege and why closing one needed the other moved (PD-166). `image_path` is a Storage object path, never a URL, and must sit under `postcards/<your uid>/`. **`created_at` and `updated_at` are SERVER-OWNED as of `044`** — `authenticated` holds SELECT and neither INSERT nor UPDATE on either, so the only value they can ever take is `default now()`. `created_at` is the home feed's sort key *and* its pagination cursor, so while it was writable an author could pin their own postcard to the top of every feed permanently (PD-163); a `default` is the value and the grant is the guarantee, because a default applies only when the column is omitted. All three verbs are now per column: `insert (id, author_id, club_id, image_path, caption, ride_id)`, `update (club_id, image_path, caption)` and — since `062` — `select (id, author_id, club_id, image_path, caption, created_at, updated_at)` — re-derive with `information_schema.column_privileges` scoped to `grantee = 'authenticated'` rather than reading this list. A per-column SELECT grant means **`select('*')` on this table is `42501` for every rider**, and a column added here is unreadable by the app until it is added to that list — the standing cost `025` first took on for `profiles`. **`author_id` and `id` lost UPDATE in `046`**, which is `045`'s rule applied to all three owner-bearing tables: **no ownership column on `postcards`, `rides` or `clubs` holds an UPDATE grant, and all three stay INSERTable** — you may declare yourself the author of a new row and may never reassign an existing one. `club_id` deliberately keeps UPDATE, because the audience is meant to be changeable and `041`'s `with check` conjunct is what guards it. **`064` adds five capture columns — `taken_at`, `taken_at_offset_minutes`, `taken_latitude`, `taken_longitude`, `taken_location_precision` — and they are INSERT-ONLY**: the grant lists become `insert (…, taken_at, taken_at_offset_minutes, taken_latitude, taken_longitude, taken_location_precision)` and `select (…, the same five)`, while **UPDATE is not mentioned by that file at all**, which is what leaves it at `046`'s three columns and makes the columns unwritable after the insert. That absence is the mechanism, not an omission — touching UPDATE is how `044` and `046` reinstated each other's lists. **`taken_at` is the one column on this table the client MUST be able to write** (the value exists only in the rider's own file, so `044`'s take-the-grant-away instrument is unavailable) and it is the ride Journal's sort key, so it is BOUNDED instead: `postcards_taken_at_is_in_the_past` refuses a future value or anything before 1995 — the year `DateTimeOriginal` was specified, which is the floor that actually catches the epoch-0 and 1904 placeholders a 1900 floor lets through. `postcards_taken_at_offset_coupling` ties the instant to the offset it was resolved with, in both directions, so the camera's wall clock is always recoverable. **The location is a PRIVACY choice made before the request is built, not a display flag** — the composer offers Hide (default, nothing is sent), a named place and Precise — **`064` shipped that middle mode as `Region`, the photo's own coordinate rounded to 2 decimal places in the browser, and `072`/`073` replaced it; the sentence you are reading describes the shipped composer, not `064`'s** — and `postcards_taken_location_coupling` plus `postcards_coarse_location_is_rounded` (renamed from `postcards_region_location_is_rounded`) are what make the middle one true against a client this app does not control. There is no "stored but hidden" state and there must never be one: RLS is row-level, so the audience of these columns IS the audience of the postcard, and `062`'s reasoning arrives inverted here — a coordinate is comparable *and* externally resolvable, and unlike `ride_id` the mitigation cannot be a grant. NULL `taken_location_precision` means Hide **and** "no EXIF location", indistinguishable on purpose. **`072`/`073` replace the middle mode with a NAMED PLACE.** `taken_place_name text null` joins the insert and select lists (UPDATE untouched again, at `046`'s three), bounded at 200 by `postcards_taken_place_name_length`; `taken_location_precision` gains `'place'` while `'region'` stays in the domain as **legacy** with no backfill. `postcards_region_location_is_rounded` is renamed `postcards_coarse_location_is_rounded` and retargeted at **both** coarse markers — it gained a subject rather than losing one, because without it a patched client could publish a front door under `'place'` labelled `Utrecht`. `postcards_taken_location_coupling` is replaced with five arms (nothing / a name with no pin / a name with a rounded pin / a precise fix, name optional / a legacy region row, name NULL). **There is deliberately NO provider-id column**: `072` added one and `073` dropped it, because a `geoapify:` id resolves through a details lookup to the feature's exact geometry and would hand back the precision the 2dp rounding exists to remove — which is why `clubs.location_place_id` and `rides.start_place_id` are NOT precedents here, both sitting beside a full-precision coordinate the rider chose to publish. `073` also fixes a `072` defect worth carrying: an arm comparing the nullable marker with `=` evaluates to NULL rather than FALSE, and **a CHECK accepts NULL**, so `072` passed the half-populated rows the coupling exists to refuse — every marker test is `is not distinct from` now, which `pg_get_constraintdef` prints as `NOT (x IS DISTINCT FROM y)`. **`074` adds `taken_country_code` — the flag half of PD-279** — ISO-3166-1 alpha-2, uppercase (`postcards_taken_country_code_is_iso_alpha2`, matching `profile_countries_code_is_iso_alpha2` from `014`/`020` rather than the vendor's own lowercase), joining the insert and select lists exactly as `taken_place_name` did and staying off UPDATE for the same reason. It is deliberately NOT folded into `postcards_taken_location_coupling` — a country is cosmetic beside the coordinate, the same way the name itself is cosmetic under `precise` — but `postcards_taken_country_code_needs_a_place` refuses one with no name, because `PostcardCard` draws the flag immediately before the town and never on its own. Set only from a PICKED or reverse-geocoded result; a typed-and-never-picked name carries no vendor data and no country. |
| `postcard_likes` | `(postcard_id, user_id)` composite PK. No denormalised count — the correct count is per-viewer, so it is counted under RLS. |
| `blocks` | `(blocker_id, blocked_id)` composite PK. The row is **directional**, the effect **symmetric**. Never query it from a policy — go through `private.is_blocked(a, b)`, which is `security definer` because the blocked party cannot read the row. |
| `postcard_comments` | A comment has no audience of its own — it **inherits the postcard's**, expressed as an `EXISTS` against `postcards` rather than a second copy of the club predicate. No UPDATE policy and no UPDATE grant: editing is not designed. No denormalised count, same reason as likes. **`created_at` and `updated_at` are server-owned as of `048`** — `insert` is per column over `(id, postcard_id, author_id, body)` and there is still no UPDATE grant of any kind. The thread sorts `created_at` **ASC**, so while it was writable a commenter could pin their comment above the comments it replies to, permanently and for every viewer; `updated_at` came out for a different reason — the table has no UPDATE path at all and its trigger is BEFORE UPDATE only, so nothing ever stamped it on insert and a comment that can never be edited could be born claiming one. |
| `postcard_hides` | `(postcard_id, user_id)` composite PK. **Per-viewer and one-directional**, unlike `blocks` — a row only ever removes a postcard from its own `user_id`'s feed. It is an input to the `postcards` SELECT policy, so `club_id` is no longer the sole determinant of what a viewer sees. |
| `profile_countries` | `(user_id, country_code)` composite PK, added by `014`. Countries a rider says they have ridden in, **entered manually** — the derived reading is unbuildable, `rides` has no country or coordinates. `country_code` is ISO 3166-1 alpha-2 with a CHECK; there is no `countries` reference table, because the picker's list is the client's and nothing joins against it. SELECT inherits the profiles predicate via `EXISTS`, so blocking works without the word appearing in the policy. |
| `clubs` (media) | `016` adds `avatar_path` and `cover_image_path`, both Storage object paths under `club-avatars/<owner uid>/` and `club-covers/<owner uid>/`. Keyed on the **uploader**, not the club, because the object must land before the club row exists; a CHECK ties each path back to the row's `owner_id`. `avatar_url` was the legacy column nothing wrote; **`024` dropped it, applied 2026-08-05**. Five query sites embedded `clubs(id, name, avatar_url)`; the three that draw an image could only ever draw initials, because it was NULL on every row — see `CLUB_EMBED_COLUMNS`. |
| `feed_reads` | The unread model, added by `015`. A **read watermark per audience**, not a row per postcard seen: `(user_id, club_id)` where `club_id` NULL is the app-wide feed, mirroring `postcards.club_id`. Its uniqueness is `unique nulls not distinct` — a plain UNIQUE treats two NULLs as different and would insert a second app-wide row on every visit. Row count is bounded by **membership**, so it never grows with content; the rejected `postcard_views` alternative grows as riders × postcards. Read it through `club_unread_counts()`, a `security invoker` function, so blocks and hides are excluded by the same policies the feed obeys. Only club rows have a writer today — the app-wide row lands with the postcard filter tiles. **`last_seen_at` is imposed by a `BEFORE INSERT OR UPDATE` trigger as of `068`** (`public.stamp_feed_read()`) and whatever the client sent is discarded. The argument is `061` §3's and it is **not** tamper-resistance: the value is compared against `postcards.created_at` and `rides.created_at`, which `044` and `045` make server-generated, so trusting the phone puts one clock on each side of a comparison and a handset running fast silently marks read whatever arrives next. A `default` cannot do that job — `015` had one and the defect shipped anyway, because a default applies only when the column is **omitted** — and neither can withholding the column grant, so **`markClubSeen` and `markFeedSeen` still SEND the column and `authenticated` keeps table-level UPDATE**: PostgREST builds `on conflict … do update set` over the columns in the request **body**, so dropping it would leave the advance on every visit after the first depending on an external tool's SET-list construction that nothing in this repo can gate. A watermark already written from a skewed clock is **not** repaired and no backfill could repair it — the true instant was never recorded anywhere — and it self-heals on that rider's next visit. **`068` also gives `club_unread_counts()` the `author_id <> auth.uid()` arm** that `061` §4 named as a candidate defect here: the reader's own postcard no longer badges their own club, which was reachable every time because a postcard is authored from `/postcards/new` rather than from inside a club. The **rides** arm deliberately keeps no `organizer_id` exclusion — `068` §2 records why that is a decision rather than the unfinished half of the same fix. |
